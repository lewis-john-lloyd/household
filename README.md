# household

Automation for household finances: ingest, compute and views over a ledger kept in Google Sheets.

The package holds logic only. All data lives in the owner's Google Drive. Notebooks in Drive install a pinned release of this package and run it under the user's own Google sign-in; nothing here stores data or credentials.

## Rules for this public repo

- No household data: no account details, amounts, names, Drive or Sheet IDs, or exports.
- Test fixtures under `tests/fixtures/` are synthetic.
- Notebooks are never committed; they hold real output.
- `tools/leak_guard.py` enforces this in CI and as a pre-commit hook. A deliberate exception is marked on its line with `leak-guard: allow`.
- `tools/push_guard.py` runs before every push (see Before pushing) and also checks against a private list of the household's real values.

## What the package can do

It runs in Colab under the owner's Google sign-in, so its reach is limited by construction:

- `tools/import_guard.py` (CI and pre-commit) allows only a short list of imports: pure standard-library modules, pandas, numpy, scikit-learn (the categorization model), pypdf, and Google's Sheets, Drive and Colab clients. No sockets, HTTP libraries, subprocesses, `os`, `eval`/`exec` or dynamic imports. Widening the list is a visible change to that file. It is an import policy that keeps changes reviewable, not a sandbox: the allowed libraries (and the Google clients' access, which is the signed-in owner's) can do whatever they do, so the boundary is reviewing a release before the notebook pins it.
- pypdf, the one library a release may download, is pinned to an exact version. pandas, numpy, scikit-learn and Google's clients come from the Colab image, bounded in `pyproject.toml` below the next major version the code hasn't been tested with (pip installs a version inside the bound if the image moves past it), and every ingest and compute logs the versions it ran with (`engine.versions`, also a `versions` row in `run_log`).
- Only the owner creates release tags, and notebooks install a tag, so nothing reaches Colab without the owner reviewing the diff (`/compare/<old tag>...<new tag>` on GitHub).

## Inbox

Files dropped in the Drive `inbox` folder are identified, checked and filed by `engine.ingest_inbox`: pay stubs in three layouts (one of them a payroll provider's earnings statement, whose PDF is read piece by piece because its layout text is unusable), a brokerage's equity award export, the accounts seed, tax returns and W-4s (filed for the record, no rows), and the IRS publications, revenue procedures, notices and public laws the tax code cites (filed under stable names such as `publication-15-t-2026`, no rows). Change sets saved from the views are read here too (see Editing in the views), oldest first. Every parser checks the document against its own printed totals; a file that fails stays in the inbox with the reason, and nothing is written. Re-sent files, and re-downloads whose rows are all already present, go to `record_store/duplicates`, except a file that was filed unread (a pay stub in a layout no parser knew yet), which is read again when it is sent again; a partially overlapping export adds only its new rows and names the earlier file it overlapped. Compute lists likely double entries (same account and amount, a few days apart, from different files) in the `possible_duplicates` report; a `void` correction takes a confirmed one off the books. See `src/household/inbox.py` and `compute.possible_duplicates`.

Bank and card downloads come in as OFX or QFX (preferred: each transaction carries the bank's own id, and the file gives the balance) or as two banks' own CSV layouts (one of them one statement per file, named with the card's last four). An OFX file is matched to its account by the last four of the account number against the `last4` column of `accounts`; a CSV names no account, so its file name must contain the `account_id` (`checking_bank.csv`). Transactions get stable ids (the bank's FITID, or account, date, amount and payee with a count for identical rows), so overlapping downloads add each transaction once. Pending rows are left out, card CSV amounts are flipped so money out is negative everywhere, and an OFX ledger balance goes to `balances`. See `parsers/ofx.py`, the CSV parsers and `ingest.finish_bank_rows`. PayPal's QIF downloads are not counted as an account (each purchase is already on the card or bank that funded it); their payments, with counterparty and item, go to `payment_details` for naming those lines.

Amazon's order history export (the zip from Request your data, or its `Order History.csv` and `Refund Details.csv` on their own) goes to `order_items`: order, ship date, the item's total, department, website and the card's last four, nothing else. The inbox files that trimmed copy in `record_store` and moves the original to Drive's trash, since the export also holds addresses, tracking numbers and the like; the same export sent again goes straight to the trash. See `parsers/amazon.py`.

Google Takeout (Google Pay and Google Play Store selected; it may arrive as several zips) goes to `order_items` too: Google Pay's list of Google purchases (Play apps and subscriptions, Google One, the Google Store), service `google`, app and item, amount and card's last four. The zips go to the trash and only those rows are filed; a part holding nothing read (the HTML index) is trashed as well. See `parsers/google_takeout.py`.

`explain.py` matches these explanation downloads to the lines they explain, by amount and date, one to one: a PAYPAL line takes PayPal's counterparty as its payee, and a GOOGLE line the app and item bought; an AMAZON charge matches a shipment (or a whole order), a credit a refund, and takes its category from the items (Whole Foods is food, a few departments map, the rest is household), split by item amount when they differ. Any store whose order history lists items works the same way: a parser that writes its orders as `order_items` rows and an entry in `explain.ORDER_SERVICES` (the store's name and the pattern of its card lines) is all it takes, and its items then show in the views as Amazon's do. An order history decides a line ahead of any payee rule, so a store asked about line by line until its export arrives is itemized once it does, and a rule for the store still decides the lines its history doesn't explain. A store with no export can still come in as a purchase list read from its account in a browser (see `parsers/target.py` for the columns): each item's amount is its share of the order total, tax and discounts included, and clothes and shoes count as clothing. Orders paid with a card that is not in `accounts` are left out. A line inside an export's dates that matched nothing is categorized like any other, except a line from a store with an order history and no payee rule (AMAZON): that one is asked about on its own in review, with the items shipped around then (closest in price first) as hints, since a gift card or a split payment can hide the order it paid for. A line after the latest export waits for the next.

## Categories and the review tab

Every transaction gets a category and a record of what decided it (`categorize.py`), first match wins: a category a person set on the line; a payee rule (`payee_rules`, a pattern with an effective date, seeded from the inbox like the accounts); an answer given in review for that payee; an explanation matched to the line (see the Inbox section; an Amazon match decides the category, a PayPal match names the payee and categorization carries on), or one still to come (Amazon, PayPal, Venmo, Apple and Google lines after their latest export wait, with a provisional guess); a scikit-learn model retrained every run on the old books and every answer since, which decides only when it is confident; and the bank's own category, as a guess. A transfer with no partner is asked about every time (money out is guessed as the household parameter `unpaired_transfer_guess`), except one dated before the other account's downloaded history begins (banks offer different lengths of history): that one is taken to be a transfer with that account, the one a household parameter `transfer_payee:<account>` names by payee or else the main account in `transfer_account`, and `transfers` lists it as `assumed_before_history`, and paper checks are asked about one by one. Lines before `REVIEW_FROM` are never asked about.

Everything else lands in the ledger's `review` tab, one row per merchant (`key`, the payee with store numbers, places and processor prefixes stripped) or per line. Type a category in `answer`, or `y` to take the guess, and run ingest: the answers are stored (`proposal_decisions` for a merchant, `txn_corrections` for a line) and the tab is rewritten with what is still open. A merchant answer covers every line from that merchant, past and future, however a card spells it: spaces and apostrophes don't count, a key covers every key that starts with it, and names a card cut short match on their first ten letters (`categorize.same_merchant`); `example` shows up to three spellings that were joined. Shorten the key before answering to widen it (`AMAZON MKTPL` to `AMAZON`). Old category names in `category_aliases` apply to rules and answers too, so renaming a category is one alias row. To split a line among categories, type the parts in its `split` column (the `answer` column has a dropdown), `kids 20; hobby 15.50; gifts 40; family`: a category and an amount for each, with at most one part left without an amount to take the rest. A sign is ignored: every part takes the line's own, so a charge's parts are charges and a refund's are refunds. The parts must come to the line's amount to the cent; a split that doesn't stays on its row with the reason. To split a line that is already decided (a rule or a merchant answer covers it), add a row to the review tab by hand with its `txn_id` (from Reports `categorized`) as `key`, `line` as `kind` and the parts in `split`. A split is stored as a `txn_corrections` row with field `split`, and the line's category and its split replace each other, so whichever was recorded later stands; budget against actual, the Sankey and the transactions list count each part in its own category. `engine.review` turns answers around without touching the inbox. The views answer the same questions without the tab (see Editing in the views).

## Budget

`budget_rules` holds one row per budget line per change: the category it pays for, the account that funds it, a priority, and a rule (`budget.py`). `fixed` is an amount per period (monthly, biweekly, annually and so on) normalized to a month; `seasonal` is the mean plus a quarter standard deviation of the category's spending in the three months centered on the same month a year earlier, the old budget-reports formula, with the amount as a fallback until there is a year of history; `trailing` is the same formula over the four months before the budget month, for spending that follows recent habits more than the season; `lookback` is the same formula over the twelve months before, a year-round average; both fall back to the amount until there is history; `sinking_fund` sets an amount aside each month and keeps a balance against the category's spending; `scheduled` puts one amount in one month (several rows for installments); `end` stops a line. A change is a new row with a later `effective`, so past targets never move. Compute writes `budget_targets` (each line each month), `budget_vs_actual` (each category each month, with its group and priority) and `sinking_funds`. The rules arrive as a seed file and are changed afterwards from the views (see Editing in the views): a change is a new row, and of two rows in one month the later one is in force, so a correction never edits a row. A later `scheduled` row on the same date replaces that amount (0 cancels it).

## The monthly checklist

Compute writes four reports for the monthly routine (`checks.py`, `recurring.py`). `coverage` lists each bank and card account that sends monthly statements with the newest date the ledger has for it, and marks it due after `max_gap_days` (45 when blank); then each explanation download with the last date it covers and how many lines wait for the next one. Set an account's `expected_docs` to `when_used` for an open card kept unused (listed, never due), or to `none` (or fill `closed`) to take it off the list. `balance_check` turns each stored balance into the balance the ledger implies before its first transaction; every snapshot of an account must imply the same one, so a later download that disagrees points at missing or doubled transactions. `paychecks` pairs each stub's net pay with its pay deposit (same amount, a few days around payday, the deposit naming the employer) and lists what doesn't pair: a deposit with no stub is "missing stub: did you forget it?", and a stub whose pay never arrived is "no deposit". `recurring` lists payees charged at a steady cadence for a steady amount, marking the ones that changed price or stopped.

## Mortgage

`mortgage.py` amortizes each loan in `loans` (principal, annual rate, term in months, origination date and the monthly escrow, mortgage insurance included, if the payment includes it) month by month from the first payment, due the second month after closing, applying `loan_events`: recorded payments (escrow comes off first; anything above the scheduled payment is extra principal), prepayments, recasts (a lump sum, then the same term at a lower payment) and rate changes. A month with no recorded payment takes the scheduled one. Compute writes the schedule (interest, principal, escrow, extra principal, balance) to the `mortgage` report beside what the household's own transactions categorized as mortgage paid that month. Loans arrive as a seed file (`loan_id,lender,originated,principal,rate,term_months,escrow`); events are typed into `loan_events`. A loan missing a field is skipped with a note.

## Pay history

The ledger's `comp_events` tab is the history of pay changes in one place: each raise, promotion, new job or schedule change, with its effective date, person, employer, annual salary, band, rating, FTE and a note. It arrives as a seed file (`effective,person,employer,salary,band,rating,fte,note`) and is kept by hand after that; nothing is computed from it.

## Receipts from email

Some stores email a receipt for every purchase. `exporter/` is a separate, small Apps Script (one file, `Code.js`) that copies new receipts into the Drive inbox once a day, as one text file per run (`receipts_<time>.txt`). It runs only the Gmail searches in its `SENDERS` script property (kept there, not in the repo, so no store is named here), holds the only Gmail permission in the system, read-only, and never changes Gmail. That permission, `gmail.readonly`, covers the whole mailbox: Gmail has no narrower scope that still shows a message's body, so `SENDERS` limits what the exporter reads, not what it could read. The boundary is the script itself, one short file to read in full before pushing it. A message it can't read is kept and fetched again by its id on every run until it reads, however far the search window has moved on, and the first time it fails the run's file notes it, so ingest's notes and the status page show the Gmail id and the error. Two exceptions, each logged in the exporter's run: a message deleted from Gmail since is no longer tried, and past 200 unreadable messages the oldest are dropped (by then the status page will have shown each one). `installTrigger` replaces only its own trigger. `exporter/test` runs it in CI against a fake Gmail and Drive. Its Drive permission is `drive.file`, which reaches only what the exporter itself created: it makes a folder of its own, `email_receipts`, on its first run, and you move that folder into the inbox once. The engine reads the inbox and the folders directly inside it. The engine keeps its Sheets and Drive access only and reads the file like any other export: `parsers/email_receipts.py` recognizes each receipt layout by its body and reads it item by item into `order_items` (one order per receipt, keyed by the message id, so a receipt exported twice is read once). A layout with no reader yet is counted in the ingest notes and left for later.

The first layout is a co-op's point-of-sale receipt (service `co_op`), which marks each item's tax class, so food, alcohol, toys and games and everything else (candles, medicine) separate, and tax and coupons are shared out so the items add to the charge. The household names the store's card lines with a ledger parameter, jurisdiction `household`, key `order_payee:co_op`, value a pattern for the payee; any store with an order history can be added the same way (`explain.order_services`), and its charges then split by what was bought like Amazon's.

The second is a bookseller's (service `bookseller`, key `order_payee:bookseller`): the receipt it emails from the register when you ask for one, read item by item at what each came to after member discounts and rewards, with the tax shared out. Toys, games and puzzles go to toys and games (family) and everything else to books (media). Its online billing summaries name the items but not their prices, so one that bills a single item reads as that item, and one that bills several is counted in the notes and stays one charge. Some stores put HTML in a receipt's plain-text part; the exporter and the reader both turn that into text.

To set it up (`npm i -g @google/clasp`, logged in):

1. `cd exporter && clasp create-script --type standalone --title "Household receipt exporter" --rootDir .`, then `clasp push`
2. In the script editor, Project Settings, Script properties: `SENDERS` (a JSON list of Gmail searches, one per store)
3. Run `exportReceipts` once. It asks for Gmail read access and access to its own Drive files, makes `email_receipts` in My Drive, and exports every receipt so far into it
4. Move `email_receipts` into the household inbox folder
5. Run `installTrigger` once to run it every morning

## The weekly email

The engine runs when you run it, so nothing else would tell you the books need attention. `nudge/` is a separate, small Apps Script (one file, `Code.js`) that sends one email on Saturday mornings listing what needs doing, grouped by what to do, or no email when nothing does. It only ever mentions things you can act on:

- **Stale for a month**: a download whose history ends more than 30 days ago (or never downloaded, with lines waiting for it); review questions whose oldest line is more than 30 days old; files that have sat in the inbox for 30 days (a file the last ingest refused is listed with the reason); an ingest more than 30 days old that compute never followed.
- **Tax, within 30 days of the deadline**: withholding projected to miss `target_refund` by more than `withholding_tolerance` (default 500), with the extra per paycheck that fixes it, in the 30 days before the year's last paycheck; a 401(k) contribution (elective or after-tax) on pace to miss or pass its limit, in the same window. These are the levers the household controls: the W-4, the WT-4, the supplemental rate for vests and bonuses, and 401(k) contributions.
- **FSA money left from last year**: every week from January 1, until it is claimed or the claim deadline passes.
- **A setting that can't be used**: a link that isn't https, a deadline that isn't a date.

Compute decides what is due and when (`nudges.py`) and publishes it to Reports as `nudges`: each item with its group, words, link and the dates between which it belongs in the email (`show_from`, `show_until`). The script keeps the rows whose dates include the day it runs, so a Reports table a few weeks old still gives the right email. It adds the three things only it can see live: inbox files (the last ingest records the inbox's folder in `run_log`, so there is nothing to set up), files ingest refused, and Reports behind the ledger. If it can't read Reports or list the inbox, the email says so rather than skipping a week.

FSA balances (`fsa_balances` in Reports) come from the pay stubs and the reimbursement deposits. A plan year's election is its deductions (the year-to-date on each person's last stub that year, plus the deductions still to come for the year in progress). A reimbursement is a deposit from the administrator (`fsa_payee_pattern`) in one of the categories each account pays (`lpfsa_categories`, `dcfsa_categories`). These are the categories you already give those deposits in Review, since one administrator pays both accounts. A deposit between January 1 and last year's claim deadline pays off last year's money first; a note such as `fsa 2026` on the transaction puts it in that plan year instead. The claim deadlines are `lpfsa_claim_deadline` and `dcfsa_claim_deadline`, each `MM-DD` of the year after the plan year, or `lpfsa_claim_deadline:2026` with a full date for one plan year. An unset deadline is taken as March 31, and the email says so.

The links and deadlines are household settings in the ledger (`settings.py`), changed in the views' Settings tab like any other edit, so neither the script nor the repo holds any of them: `views_url` (links open the right page, such as `?view=edit&tab=review`), `payroll_url`, `benefits_url` and `fsa_claims_url`. The Settings tab lists every known setting, set or not, with what it is for. The script's permissions are Reports read-only, Drive file names and dates (never contents), sending mail to you, and its own trigger. `nudge/test` runs it in CI against faked Sheets, Drive and mail.

To set it up (`npm i -g @google/clasp`, logged in):

1. `cd nudge && clasp create-script --type standalone --title "Household weekly email" --rootDir .`, then `clasp push`
2. In the script editor, Project Settings, Script properties: `REPORTS_ID`, the same id the views use
3. Run `preview` once. It asks for its permissions, then logs the email it would send today
4. Run `installTrigger` once to send it every Saturday at 7 in the morning
5. In the views' Settings tab, set the links and the FSA settings

## Views

Compute writes each view's data as a Reports table, and `web/` draws it: a TypeScript Apps Script web app that reads Reports under the viewer's own Google sign-in and draws with Google Charts. It opens on a status page, in Material 3 (light or dark with the system): the latest ingest and compute, from `run_log` (each stage's summary, as JSON) and `run_notes` (every line each printed), with a card for each thing that needs you (lines open in review, downloads due, balances or tax lines that disagree, unexplained withholding, inbox files not read, transfers with no partner, saved changes ingest refused). A card says what it counts in words and lists the things themselves where Reports has them (each download due from `coverage`, with how far it reaches and how many lines wait for it; how the review questions split from `editor_review`), with a button to the Edit tab that answers it. Below them, how lines since `REVIEW_FROM` were categorized (your answers, receipts and order histories, payee rules, transfers, the model, and what still waits), the tax projection as bars from zero (a refund left, an amount owed right), and both runs' full logs, open, with the lines behind each card marked; it says so when compute hasn't run since the last ingest. The next view is the `flows` table (`flows.py`) as a Sankey: pay through taxes, deductions and net pay into the accounts (vested shares go straight to savings), then out to savings and each category (savings categories also flow back in, as shares sold; a category that got more back than it spent shows as money back; whatever the period didn't cover came from or went to cash balances), for any month, any year, or a year's monthly average (the year divided by the months it has data for), by category or by group, each node labeled with its total. Under the chart, the same money by what it is to the household, in three columns: what came in (pay, shares sold, money back, cash already in the accounts), taxes and deductions, and where it went (each category, savings, vested shares, cash left in the accounts), each with its total and a bar per line, and the stops on the way (net pay, accounts) in a line below (`shape.flowSummary`). A year takes each pay line's year-to-date amount from the year's last stub, so a missing stub doesn't shrink the year, and pay deposits no stub accounts for show as "pay without a stub (person)", matched to a person by their employer's name on the deposit. The third is budget against actual from `budget_vs_actual`: one line per category or group for a month or a year so far, with its budget, what was spent, what is left and a bar for how much is used, over-budget lines first within each priority, every column sortable. Clicking a line lists its transactions for the period from `categorized` (a split charge counts its part); a charge an order history explains (any store in `explain.ORDER_SERVICES`) lists the items it bought under its payee, each part of a split only the items in its category, from `categorized.items` (five, then "+N more" to show the rest). A part of a split charge is marked split, its parts listed on hover, and hovering a transaction shows its txn_id, which a click copies; "edit" on a transaction corrects it (see Editing in the views). Transfers and income are left out; a category with spending but no budget shows as such. `web/src/shape.ts` turns rows into chart and table data and `web/src/edits.ts` builds change sets; both are tested under Node. `web/test/browser` drives the built page in Chromium with the server calls faked, each answer held back at will, to test what a person meets: a change made while Save runs stays for the next save, a failed save keeps every change and the next Save checks whether it landed, a past year's tax page has no scenario to choose, and a load that fails says so (`npm run test:browser` after `npm run build`; CI runs it). `web/test/server` runs the built server code under Node with Apps Script's services faked, the user property store holding to its limits (9 KB a value, 500 KB in all): each saved change set keeps its own small record (its edits in words, as many as fit, and how many more), the oldest past 40 are dropped and filed ones tidied, and once the file is in Drive a save never reports failure (a record that can't be kept comes back as a warning); the same request saved twice writes one file, found again by its request after ingest has moved it. Change sets carry their time to the millisecond, one person's are strictly in order, and each file name ends in a short unique suffix. A tab that doesn't exist yet reads as empty, but any other failure to read Reports is reported, never shown as empty data. No IDs or data live in `web/`.

### Taxes

The Taxes view is this year's return worked out from the pay stubs, vests, sales and your estimates (`projection.py`), and a status card links to it:
- **Both returns line by line.** Form 1040 from wages to the refund or amount owed, the Schedule A, D and 2 lines it uses, and Wisconsin Form 1 from Wisconsin income to the balance (`tax_lines` in Reports), as things stand. Wisconsin's line numbers come from the blank Form 1 on file and are cited like tax law (`taxdata.FORM_LINES`, checked by `tools/verify_tax_law.py`); a year whose form isn't on file yet uses the latest form's numbers, and the page says so. This year's scenarios (no extra withholding, vests at 22%, stock 20% higher or lower) are compared by their totals in a panel of their own; the forms never change with them, and rows for any other scenario an older compute left in `tax_lines` are ignored.
- **Last year beside your filed return.** While last year's stubs are in the ledger, the page works out last year from them, with no scenarios (it is over), and once its filed lines are in `return_facts` it shows each filed value beside them with what's off.
- **Withholding for the rest of the year.** For each return, the W-4 Step 4(c) or WT-4 additional amount per paycheck that lands the year on a refund of `target_refund` (a household setting, 2,000 unless set), on no balance, and on owing that much, from the year so far plus the projection with future vests withheld at `planned_supplemental_rate` (35% unless set), on the paychecks of whoever has the most left (`withholding_plan`). A target withholding can't reach says how close it gets, and a federal balance owed says whether it escapes the underpayment penalty (owing under 1,000, or withholding at least the smaller of 90% of this year's tax and last year's safe harbor; Pub 505, cited).
- **Retirement and health accounts.** The 401(k), the mega backdoor Roth (after-tax 401(k) contributions against what 415(c) leaves, marked converted when the household setting `after_tax_401k_converts_to_roth` is TRUE, since a stub can't show a conversion), the HSA, a limited-purpose or health FSA (against the year's health FSA limit, per person and employer) and the dependent-care FSA, each so far this year and by December 31 against its limit (`elections`). A backdoor Roth IRA isn't on a pay stub, so it shows as not tracked.

### Editing in the views

The Edit view changes the ledger without opening it: answering review questions (a merchant, or one line, which can be split), budget lines (change from a date, end, or schedule a one-off amount; an amount on a date that has one replaces it, and says what it replaced), payee rules (change or stop), categories and old names, household settings, withholding explanations and possible duplicates. Each tab is a list on the left, one row per item with a line about it and a count and filter at the top, and the chosen item's editor on the right (on a phone, the editor replaces the list). A transaction's id in the budget drill-down opens its own page: what it bought, each item with its category to change (kept with the item in the ledger's `item_categories`, so the line, split by its items, follows once ingest and compute run, and the split editor below previews it at once), one category for it (or for every line from its merchant), a split editor that adds the parts up against the line as you type (or splits it by what an order history says it bought), its note and one-off flag, or drop it as a duplicate. Edits stay in the page, listed in a bar at the bottom, until Save; leaving with unsaved edits asks first.

The views still never write the ledger. Save writes one change set, `changes_<time>Z.json`, into the views' own Drive folder, and ingest, the only writer of the ledger, reads it from the inbox (`parsers/changes.py`). Each edit becomes the one row a person would have typed (`proposal_decisions`, `txn_corrections`, `budget_rules`, `payee_rules`, `categories`, `category_aliases`, `parameters`), recorded at the time it was saved, and each is logged as ingest writes it. The views' Drive permission is `drive.file`, so they reach only files they made: the first Save makes a folder `web_edits` in My Drive, and you move it into the household inbox once, as with `email_receipts`. The Saved tab, and a card on the status page, list change sets ingest hasn't read yet. Each Save carries an id the browser made for it, kept on the file in Drive: the same id saved again answers with the file it already wrote. When a Save fails, its answer may have been lost after Drive had the file, so the next Save first asks whether that request landed (`findSave`, which waits for a Save still running) and writes nothing twice. A file it finds in the trash reads as discarded, never as saved, and the changes stay for the next Save. Discard all never drops what a save may have written: while a save or that check runs, Save and Discard all wait, and an edit sent in a save that hasn't answered can't be undone. After a save that didn't confirm, Discard all first checks it; if it landed, its changes are saved, and the page offers to discard that change set too (`discardWaiting`). Discarding puts the file in the trash, so no ingest from then on reads it; an ingest already running may have downloaded it first and still apply it, and nothing in Drive can stop that. So the views remember each discard for thirty days, and when the ledger holds a discarded change set, the status page says it was applied anyway, with its edits, so the settings can be edited back. The ledger is the record here, not the run_log: each ingest publishes `changes_written` to Reports from `source_documents` (the last 45 days), so a later run can't hide one, and one whose rows were written but whose filing in Drive failed is there too (the run_log marks those `written` as well). It matches by Drive file id, not name. Ingest writes all of a run's ledger rows, each file's `source_documents` row with them, in one atomic Sheets write (`sheets.append_tables`): a failure leaves the ledger as it was, so a change set's edits can't land without the record of them. A discard the views can't remember says so, rather than promising the status page will tell. Leaving the page warns while a save is unanswered. A change set saved before the last ingest that the ingest never listed is marked as unseen, on the status page and in the Saved tab: ingest reads only the inbox and the folders directly in it, so `web_edits` is still in My Drive.

A change set fails closed. It is strict JSON in a declared format and version, with no unknown fields, size and count limits, and rows written as text (never formulas). Every value is checked alone (dates, enums, patterns that compile and stay short, splits that read), then against the ledger (categories and old names that exist, transactions and stubs that exist, splits that add up to the line). An edit that replaces a setting carries the fields of the row it replaced (`was`), a scheduled amount included, since the budget keeps the last amount on a date (`editor_scheduled` in Reports lists those in force); if the ledger has moved on since (another change set, or a seed), the edit is stale. One change set edits each setting once, by the same target the editor stages by (`editTarget`; a scheduled amount is one per line and date, a pair of lines one pair either way round). One bad or stale edit refuses the whole file, which stays in the inbox with every reason, shown on the status page and in the Saved tab, where Discard moves it to the trash. Compute publishes what the editors show as `editor_*` tables in Reports: each setting's row in force, each budget line in words with this month's target and the last twelve months' spending, and the review queue. Accounts, loans, pay history and allocation targets still arrive as seed files.

To deploy (Node 22 and `npm i -g @google/clasp`):

1. `cd web && npm ci && npm run build`
2. `clasp login`, then `clasp create-script --type webapp --title "Household views" --rootDir dist` (or copy `.clasp.json.example` to `.clasp.json` with an existing script id)
3. `clasp push` (or `npm run push`, which builds first)
4. In the script editor, Project Settings, Script properties: add `REPORTS_ID` with the Reports spreadsheet's id
5. Deploy, New deployment, Web app. It runs as the person viewing it, so they see only what they can open; `access` in `appsscript.json` is `MYSELF` (only the owner). To let another household member open it, set `ANYONE` (any signed-in Google account; Reports' own sharing still decides who can read it) and redeploy.
6. After a change: check out the release tag, `npm run push`, then `clasp update-deployment <deployment id>` (`clasp list-deployments` shows it), so the web app's URL stays the same. A release that adds a permission (editing added `drive.file` and the Drive service) asks for it again the next time the page opens.

## Tax law

Federal and state rates, limits and withholding tables live in `src/household/taxdata.py`; each state's return and withholding method is in a module of its own. Every value cites the page of a source document that states it (`CITATIONS`), and each source is pinned by the SHA-256 of the PDF it was checked against (`DOCUMENTS`). The `tax_sources` report lists every value with its citation and a link to the PDF in the record store.

A release that changes tax law (each January) adds the new year's values and citations, then checks them against the PDFs:

```
python tools/verify_tax_law.py <folder of source PDFs>
```

It checks that each quote is on its cited page and states the value the code uses, that every bracket threshold appears, and that every row of Pub 15-T's annual married-filing-jointly table equals the brackets shifted by the table floor. Where a state prints no rate schedule or deduction formula, those are proved by reproducing every row of its printed tables and the amounts in its worksheets. It exits nonzero on any failure, missing document, or uncited value.

## Before pushing

This repo is public, so hooks check for household data before it can leave the machine. Binary files (PDFs, images, office files, archives) are refused outright unless `tests/fixtures/BINARIES` lists them as made-up fixtures, and a listed PDF's text is checked like any other file: real statements and exports are binary, and line checks can't see inside them. Turn them on once per clone with `git config core.hooksPath .githooks`. The pre-commit and commit-msg hooks run the text checks below on the staged changes and the message (`push_guard.py --staged`, `--message`), so a value is caught before it is in a commit; the pre-push hook runs everything again as the backstop. `tools/push_guard.py` checks every added line and commit message against the leak guard's patterns and against a private denylist of the household's real values (names, places, employers, account digits, and every amount with cents in the pay stubs and transactions, however it is written), kept outside the repo at `~/.config/household/denylist.txt`; then it runs the import guard and the tests. `tools/denylist.py` builds the denylist from ledger exports and a words file, and adds every category in a personal group (`personal`, `family_support`), since those are named for people. Examples and tests use made-up names and categories only (CLAUDE.md lists them); a GitHub address is not checked, since it is public. Without a denylist the push stops (`HOUSEHOLD_NO_DENYLIST=1` skips that check; `HOUSEHOLD_PUSH_QUICK=1` skips the tests).

## Releases

Notebooks pin a tag, for example `pip install git+https://github.com/lewis-john-lloyd/household@v0.0.1`. Upgrading is a deliberate edit of that tag; rolling back is reverting it.

Ordinary commits leave the version number alone. When work is ready to run, one release commit sets the version in `pyproject.toml` and `household/__init__.py`, and the owner tags that commit.
