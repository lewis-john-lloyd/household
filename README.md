# household

Automation for household finances: ingest, compute and views over a ledger kept in Google Sheets.

The package holds logic only. All data lives in the owner's Google Drive. Notebooks in Drive install a pinned release of this package and run it under the user's own Google sign-in; nothing here stores data or credentials.

## Rules for this public repo

- No household data: no account details, amounts, names, Drive or Sheet IDs, or exports.
- Test fixtures under `tests/fixtures/` are synthetic.
- Notebooks are never committed; they hold real output.
- `tools/leak_guard.py` enforces this in CI and as a pre-commit hook. A deliberate exception is marked on its line with `leak-guard: allow`.
- `tools/push_guard.py` runs before every push (see Before pushing) and also checks against a private list of the household's real values.

## What the package can do

It runs in Colab under the owner's Google sign-in, so its reach is limited by construction:

- `tools/import_guard.py` (CI and pre-commit) allows only a short list of imports: pure standard-library modules, pandas, numpy, scikit-learn (the categorization model), pypdf, and Google's Sheets, Drive and Colab clients. No sockets, HTTP libraries, subprocesses, `os`, `eval`/`exec` or dynamic imports. Widening the list is a visible change to that file. It is an import policy that keeps changes reviewable, not a sandbox: the allowed libraries (and the Google clients' access, which is the signed-in owner's) can do whatever they do, so the boundary is reviewing a release before the notebook pins it.
- pypdf, the one library a release may download, is pinned to an exact version. pandas, numpy, scikit-learn and Google's clients come from the Colab image, bounded in `pyproject.toml` below the next major version the code hasn't been tested with (pip installs a version inside the bound if the image moves past it), and every ingest and compute logs the versions it ran with (`engine.versions`, also a `versions` row in `run_log`).
- Only the owner creates release tags, and notebooks install a tag, so nothing reaches Colab without the owner reviewing the diff (`/compare/<old tag>...<new tag>` on GitHub).
- CI's token can only read the repo, and every action it uses is pinned to a commit, not a tag that could be moved (`tests/test_ci.py` holds both). To update an action, look up the commit its new tag points to (`git ls-remote --tags https://github.com/actions/<name>`).

## Where the data lives, and for how long

Everything is in the owner's Google Drive, under the household folder, and nothing about the household is in this repo or the scripts. Who can see it is decided by Drive sharing, not by this code: share that folder only with the people who keep the books, and look at its sharing now and then. Each part, and how long it stays:

- `inbox`: files waiting to be read. Read files leave it; a refused one stays, with its reason, until it is fixed or deleted.
- `record_store`: every file ingest read, filed under a descriptive name and kept for good, so the ledger can be rebuilt from it.
- The ledger and Reports: the ledger keeps every row; a correction is a new row, so an earlier value stays in the sheet. Reports is rebuilt by every compute.
- `backups`: one zip of every ledger tab per ingest, kept for good. Each holds everything the ledger held then, so it is as sensitive as the ledger, and a value corrected since is still in the older zips.
- Drive's trash: the Amazon and Google exports go there once their trimmed copies are filed (the originals hold addresses and more). Drive empties its trash after 30 days; until then a file can be restored. Empty the trash to remove them sooner.
- Gmail: the receipts the exporter reads stay in Gmail as they were, and the weekly email puts the household's to-dos (balances, withholding, FSA money left) in the inbox it is sent to.

To remove something for good, it has to go from the ledger, from `record_store` and from every backup that holds it, by hand.

## Inbox

Files dropped in the Drive `inbox` folder are identified, checked and filed by `engine.ingest_inbox`: pay stubs in three layouts (one of them a payroll provider's earnings statement, whose PDF is read piece by piece because its layout text is unusable), a brokerage's equity award export, the accounts seed, tax returns and W-4s (filed for the record, no rows), and the IRS publications, revenue procedures, notices and public laws the tax code cites (filed under stable names such as `publication-15-t-2026`, no rows). Change sets saved from the views are read here too (see Editing in the views), oldest first. Every parser checks the document against its own printed totals; a file that fails stays in the inbox with the reason, and nothing is written. Re-sent files, and re-downloads whose rows are all already present, go to `record_store/duplicates`, except a file that was filed unread (a pay stub in a layout no parser knew yet), which is read again when it is sent again; a partially overlapping export adds only its new rows and names the earlier file it overlapped. Compute lists likely double entries (same account and amount, a few days apart, from different files) in the `possible_duplicates` report; a `void` correction takes a confirmed one off the books. See `src/household/inbox.py` and `compute.possible_duplicates`.

Bank and card downloads come in as OFX or QFX (preferred: each transaction carries the bank's own id, and the file gives the balance) or as two banks' own CSV layouts (one of them one statement per file, named with the card's last four). An OFX file is matched to its account by the last four of the account number against the `last4` column of `accounts`; a CSV names no account, so its file name must contain the `account_id` (`checking_bank.csv`). Transactions get stable ids (the bank's FITID, or account, date, amount and payee with a count for identical rows), so overlapping downloads add each transaction once. Pending rows are left out, card CSV amounts are flipped so money out is negative everywhere, and an OFX ledger balance goes to `balances`. See `parsers/ofx.py`, the CSV parsers and `ingest.finish_bank_rows`. PayPal's QIF downloads are not counted as an account (each purchase is already on the card or bank that funded it); their payments, with counterparty and item, go to `payment_details` for naming those lines.

Amazon's order history export (the zip from Request your data, or its `Order History.csv` and `Refund Details.csv` on their own) goes to `order_items`: order, ship date, the item's total, department, website and the card's last four, nothing else. The inbox files that trimmed copy in `record_store` and moves the original to Drive's trash, since the export also holds addresses, tracking numbers and the like; the same export sent again goes straight to the trash. See `parsers/amazon.py`.

Fidelity's account history (Accounts, History, Download: `History_for_Account_<number>.csv`, for a brokerage account, an IRA or an HSA) and a workplace plan's history in Quicken's investment format (`.qif`) go to `investment_activity`, one row per thing that happened, in one vocabulary for both: its kind (contribution, buy, sell, exchange, reinvest, dividend, interest, conversion in or out, transfer in or out, withdrawal, fee, adjustment), the change in shares of its fund and their value, and the money crossing the account's edge (in positive, out negative; buying, selling and exchanging inside the account move none). A history file finds its account by the last four of the number in its name, against the accounts table's `last4`; a plan's QIF names no account, so its file name must carry the account_id (`m_401k_old.qif`). Overlapping downloads add each row once (a history row is keyed with its running cash balance, a QIF row on all its fields). Compute sums each account's money in and out by year and kind into `investment_flows`, and logs the contributions, conversions and withdrawals. See `parsers/fidelity.py`.

An OFX or QFX investment download (Vanguard's puts every account in one file) is read by `parsers/ofx_invest.py` into the same `investment_activity`, plus each account's positions as `holdings` and every price the file states as `prices` (the only prices a plan-only trust fund has). Each statement finds its account by the last four of its number in the accounts table's `last4`, so one file can fill several accounts. A workplace plan's rows keep their money source (`source`: pretax, match, aftertax, rollover, as the custodian names it); a plan is kept as one account and its parts are told apart by source. In a plan, a buy is payroll money coming in (a contribution) and a transfer moves shares between funds or sources inside it. Elsewhere, a deposit that shows up only as a sweep into the settlement fund is read as a contribution, worked out from the cash the account had on hand, and a transfer out of a pre-tax account matched by one into a Roth account on the same day is a conversion. A transaction the file lists twice, identical to its FITID, is read once (Vanguard repeats every trust-fund transaction).

HealthEquity's "All Investment Transactions" download (`.xlsx`) is read by `parsers/healthequity.py`: a Buy moves the HSA's cash into its fund (no money in or out), a Dividend is reinvested, each row's running Total Shares is checked against the row before, and each fund's last total is a `holdings` reading. The file names no account, so its name carries the account_id (`l_hsa_healthequity.xlsx`). The inbox reads any `.xlsx` as CSV text of its first sheet (`xlsx.py`, standard library only).

Schwab's Equity Award Center transaction export, CSV or JSON, is read by `parsers/schwab_equity.py` into `equity_vests` and `equity_sales` (each sale's lots must add up to its shares and proceeds). Equity grants' vesting schedules come from Schwab's Awards page: copy each grant's details (award, Award ID with vested, unvested and canceled, and the Vesting Schedule) as text into a `.txt` and drop it in the inbox. `parsers/schwab_awards.py` checks that each grant's schedule and its vested, unvested and canceled shares add up to the shares granted, and writes `vest_schedule` (grant, award date, symbol, type, vest date, shares); a grant's rows from its latest copy are its schedule. The tax projection then takes the vests left this year from the schedule at the 12-month average share price (the last price of each month in the year, from vests' fair market values and closes in `prices`), in place of one a month at the recent average.

A Vanguard workplace plan's quarterly statement (PDF) is read by `parsers/vanguard_plan.py` for what the plan's download lacks: the balance in each money source at the quarter's end (pre-tax, match, rollover, after-tax, each year's Roth in-plan conversion), each a `holdings` reading with no fund and the source's name as `source`. Every source and fund row must add up, the sources to the Total Value and the funds to the Total Invested, or the statement is refused. The plan's number in the header finds its account by `last4`.

Edvest's 529 account download (`ofxdownload_MMDDYYYY.csv`: positions, then transactions) is read by `parsers/edvest.py`: contributions are money in, a rollover from another plan is a transfer in, a K-12 or college withdrawal is money out, and the positions are `holdings` dated from the download's name (keep it). A portfolio has no ticker, so its name is its symbol. The account is found by the last four digits of the account number.

HealthEquity's HSA cash history (the yearly "Completed Transactions" download, `TransactionHistory.xls`, an HTML table) is read by `parsers/healthequity_cash.py`: contributions and interest are money in, fees and claims paid money out, and an Investment row is the cash moving into a fund (inside the account). Read oldest first, each row's balance must follow from the one before; the newest balance is a `cash` holdings reading. The file names no account, so it is matched to the one HealthEquity account in the accounts table, or by an account_id in its name.

Fidelity's Positions download (`Portfolio_Positions_<date>.csv`) is read by `parsers/fidelity_positions.py`: every account's holdings on the download date, a money market held as cash at a share a dollar, and a plan's fund by its code (NON40OJU1 as OJU1, as the plan's QIF names it); each account by the last four digits of its number.

A stock option grant's schedule, copied as text from the plan's Stock Options page into a `.txt`, is read by `parsers/stock_options.py` into the same `vest_schedule` (award type OPTION, with its grant price and expiry); the tranches must add up to the grant. An option vesting is no income, so the tax projection takes only share awards (RSU, PSU) from the schedule.

Holdings and prices sit beside the activity. The ledger's `securities` tab lists each fund or stock with its name, asset class, expense ratio and `quote`, the symbol GOOGLEFINANCE knows it by (blank for a fund with no public price, such as a plan-only trust). `holdings` keeps readings of what an account held on a date: shares and value per fund, or a value alone. The legacy investments workbook comes in through `engine.ingest_legacy_investments(session, folder_id, workbook_id, tabs)`, which the engine notebook runs every time (with nothing new it writes nothing), where `tabs` maps each account tab to its account_id (`{"alex-ira": "a_ira"}`; several tabs can map to one account, and their readings on a date add up): its funds tab becomes `securities`, each fund quoted by its own symbol, and each tab's dated rows become `holdings` (`legacy_investments.py`). A target-date fund kept as its share of each underlying fund comes in as those values, with no shares. Running it again adds nothing. Prices come from GOOGLEFINANCE through Sheets, so the engine never reaches the network itself: each ingest writes one formula per quoted security and date still wanted into the ledger's `price_requests` tab, waits up to a minute for Sheets to work them out, reads the answers into `prices` (the close on or before the date, the trading day it came from, and the source), and rewrites the tab with what is left for the next ingest, at most 600 at a time. The formula is built from the quote and date alone, each checked first, and `price_requests` is the one tab a formula is ever written to. Prices are wanted on every date the legacy workbook recorded, then at each month-end after the last of those (from the first holdings or activity when there is no legacy workbook), and each security's latest close, asked each day ingest runs, so the 12-month average the tax projection prices vests at runs to the market's latest close. `engine.fetch_prices` asks round after round until none is wanted, for a backfill in one call. A date GOOGLEFINANCE has no price for is kept as a row with no close, so it is not asked again; delete the row to ask again. A fund's close is its NAV, unadjusted, which is what its shares are worth. See `prices.py`.

Google Takeout (Google Pay and Google Play Store selected; it may arrive as several zips) goes to `order_items` too: Google Pay's list of Google purchases (Play apps and subscriptions, Google One, the Google Store), service `google`, app and item, amount and card's last four. The zips go to the trash and only those rows are filed; a part holding nothing read (the HTML index) is trashed as well. See `parsers/google_takeout.py`.

`explain.py` matches these explanation downloads to the lines they explain, by amount and date, one to one: a PAYPAL line takes PayPal's counterparty as its payee, and a GOOGLE line the app and item bought; an AMAZON charge matches a shipment (or a whole order, or one item of a shipment for a store that charges each part on its own), a credit a refund, and takes its category from the items (Whole Foods is food, a few departments map, the rest is household), split by item amount when they differ. Any store whose order history lists items works the same way: a parser that writes its orders as `order_items` rows and an entry in `explain.ORDER_SERVICES` (the store's name and the pattern of its card lines) is all it takes, and its items then show in the views as Amazon's do. An order history decides a line ahead of any payee rule, so a store asked about line by line until its export arrives is itemized once it does, and a rule for the store still decides the lines its history doesn't explain. A store with no export can still come in as a purchase list read from its account in a browser (see `parsers/target.py` for the columns): each item's amount is its share of the order total, tax and discounts included, and clothes and shoes count as clothing. Orders paid with a card that is not in `accounts` are left out. A line inside an export's dates that matched nothing is categorized like any other, except a line from a store with an order history and no payee rule (AMAZON): that one is asked about on its own in review, with the items shipped around then (closest in price first) as hints, since a gift card or a split payment can hide the order it paid for. A line after the latest export waits for the next; a line before the earliest goes to review, since nothing will ever cover it. A Venmo cash-out is always asked about on its own, since each carries whatever came in since the last. A PayPal, Venmo, Apple or Google line nothing names is asked about on its own, not as one merchant, since its payee names only the service (an answer already given for the merchant still covers it).

## Categories and the review tab

Every transaction gets a category and a record of what decided it (`categorize.py`), first match wins: a category a person set on the line; a payee rule (`payee_rules`, a pattern with an effective date, seeded from the inbox like the accounts); an answer given in review for that payee; an explanation matched to the line (see the Inbox section; an Amazon match decides the category, a PayPal match names the payee and categorization carries on), or one still to come (Amazon, PayPal, Venmo, Apple and Google lines after their latest export wait, with a provisional guess); a scikit-learn model retrained every run on the old books and every answer since, which decides only when it is confident; and the bank's own category, as a guess. A transfer with no partner is asked about every time (money out is guessed as the household parameter `unpaired_transfer_guess`), except one dated before the other account's downloaded history begins (banks offer different lengths of history): that one is taken to be a transfer with that account, the one a household parameter `transfer_payee:<account>` names by payee or else the main account in `transfer_account`, and `transfers` lists it as `assumed_before_history`, and paper checks are asked about one by one. Lines before `REVIEW_FROM` are never asked about.

Everything else lands in the ledger's `review` tab, one row per merchant (`key`, the payee with store numbers, places and processor prefixes stripped) or per line. Type a category in `answer`, or `y` to take the guess, and run ingest: the answers are stored (`proposal_decisions` for a merchant, `txn_corrections` for a line) and the tab is rewritten with what is still open. A merchant answer covers every line from that merchant, past and future, however a card spells it: spaces and apostrophes don't count, a key covers every key that starts with it, and names a card cut short match on their first ten letters (`categorize.same_merchant`); `example` shows up to three spellings that were joined. Shorten the key before answering to widen it (`AMAZON MKTPL` to `AMAZON`). Old category names in `category_aliases` apply to rules and answers too, so renaming a category is one alias row. To split a line among categories, type the parts in its `split` column (the `answer` column has a dropdown), `kids 20; hobby 15.50; gifts 40; family`: a category and an amount for each, with at most one part left without an amount to take the rest. A sign is ignored: every part takes the line's own, so a charge's parts are charges and a refund's are refunds. The parts must come to the line's amount to the cent; a split that doesn't stays on its row with the reason. To split a line that is already decided (a rule or a merchant answer covers it), add a row to the review tab by hand with its `txn_id` (from Reports `categorized`) as `key`, `line` as `kind` and the parts in `split`. A split is stored as a `txn_corrections` row with field `split`, and the line's category and its split replace each other, so whichever was recorded later stands; budget against actual, the Sankey and the transactions list count each part in its own category. `engine.review` turns answers around without touching the inbox. The views answer the same questions without the tab (see Editing in the views).

## Budget

`budget_rules` holds one row per budget line per change: the category it pays for, the account that funds it, a priority, and a rule (`budget.py`). `fixed` is an amount per period (monthly, biweekly, annually and so on) normalized to a month; `seasonal` is the mean plus a quarter standard deviation of the category's spending in the three months centered on the same month a year earlier, the old budget-reports formula, with the amount as a fallback until there is a year of history; `trailing` is the same formula over the four months before the budget month, for spending that follows recent habits more than the season; `lookback` is the same formula over the twelve months before, a year-round average; both fall back to the amount until there is history; `sinking_fund` sets an amount aside each month and keeps a balance against the category's spending; `recurring` is the recurring charges you track in the category (see below), each at its latest price on a monthly footing (a yearly one is a twelfth a month), plus the amount as an allowance for the rest of its spending, so a price change moves the target with it (`recurring.monthly_expected`); `scheduled` puts one amount in one month (several rows for installments); `end` stops a line. A change is a new row with a later `effective`, so past targets never move. Compute writes `budget_targets` (each line each month), `budget_vs_actual` (each category each month, with its group and priority), `sinking_funds`, and `daily_actuals` (every day's spending per category, every era, transfers and income left out) for the Budget page's comparisons. The rules arrive as a seed file and are changed afterwards from the views (see Editing in the views): a change is a new row, and of two rows in one month the later one is in force, so a correction never edits a row. A later `scheduled` row on the same date replaces that amount (0 cancels it).

## The monthly checklist

Compute writes four reports for the monthly routine (`checks.py`, `recurring.py`). `coverage` lists each bank and card account that sends monthly statements with the newest date the ledger has for it, and marks it due after `max_gap_days` (45 when blank); then each explanation download with the last date it covers and how many lines wait for the next one. Set an account's `expected_docs` to `when_used` for an open card kept unused (listed, never due), or to `none` (or fill `closed`) to take it off the list. `balance_check` turns each stored balance into the balance the ledger implies before its first transaction; every snapshot of an account must imply the same one, so a later download that disagrees points at missing or doubled transactions. `paychecks` pairs each stub's net pay with its pay deposit (same amount, a few days around payday, the deposit naming the employer) and lists what doesn't pair: a deposit with no stub is "missing stub: did you forget it?", and a stub whose pay never arrived is "no deposit". `recurring` lists payees charged at a steady cadence for a steady amount, marking the ones that changed price or stopped. Those are suggestions: the Budget page's Recurring tab tracks a merchant (review's name for it, such as APPLE ONE) as a recurring charge or not, whether it is a mortgage, a lease, insurance or a streaming service (a `subscription` edit, kept in `proposal_decisions`; the internal names keep the word so marks already saved still count), offers each charge that recurs and is not tracked either way (track it, merge it into one that is, or turn it down; the ones that seem to have stopped, with no charge for 1.5 cadences, are listed apart), and opens any charge for its forms. Two entries that are one charge (a new name on the statement, a loan that was sold) are merged there: a `recurring_merge` edit (kept in `proposal_decisions` as `subscription_merge:<key>`, the key it joins in its note) adds one key's charges to another's, so they have one history, cadence and price change; an empty `same_as` separates them again (`recurring.merges`). The tab lists what you track by the budget line it belongs to (`recurring.subscriptions`, the `subscriptions` table): each with its cadence, latest charge, next charge expected and yearly cost (the latest charge times the charges a year, or the last 365 days when irregular), and the yearly total of the ones still charged. When a charge differs from the one before by more than 3% (and 50 cents), the tab shows the change and what it means for its line (a `recurring` line follows it; a fixed one is offered the new amount), and for 45 days after the charge a status card and the weekly email say so. On the Budget page, each tracked charge is its own entry under its category's line, with what it spent and what its cadence expected (`subscription_months`: the last charge for a monthly one, and for a yearly or quarterly one the last charge in the month it fell due); its spending is part of the line above.

## Mortgage

`mortgage.py` amortizes each loan in `loans` (principal, annual rate, term in months, origination date and the monthly escrow, mortgage insurance included, if the payment includes it) month by month from the first payment, due the second month after closing, applying `loan_events`: recorded payments (escrow comes off first; anything above the scheduled payment is extra principal), prepayments, recasts (a lump sum, then the same term at a lower payment) and rate changes. A month with no recorded payment takes the scheduled one. Compute writes the schedule (interest, principal, escrow, extra principal, balance) to the `mortgage` report beside what the household's own transactions categorized as mortgage paid that month. Loans arrive as a seed file (`loan_id,lender,originated,principal,rate,term_months,escrow`); events are typed into `loan_events`. A loan missing a field is skipped with a note.

## Pay history

The ledger's `comp_events` tab is the history of pay changes in one place: each raise, promotion, new job or schedule change, with its effective date, person, employer, annual salary, band, rating, FTE and a note. It arrives as a seed file (`effective,person,employer,salary,band,rating,fte,note`) and is kept after that on the Jobs page of the views (a `job` edit; a row for the same date, person and employer corrects the earlier one), or by hand. Salary is the full-time salary a year and FTE the share of full time (blank is full time). The tax projection reads it for one thing: a job goes on until the person's next row for another employer (a raise at the same employer ends nothing), so a new job should get a row on the day it starts. Compute also sets the stubs beside it (`paycheck.py`, the `pay_check` table): each regular paycheck's base pay (salary, regular hours and paid time off) on a yearly footing by its pay period, against the row in force on the period's first day (salary times FTE). Two or more paychecks in a row with the same pay are a salary run, which disagrees when it is off by more than half a percent (a raise shows); the rest under one row, three or more, are hourly, and their median disagrees when off by more than 5% (hours vary). A job's first and last paychecks are left out as partial, and only paychecks since January 1 of last year are judged. The Jobs page shows a chart of each person's pay a year (salary times FTE) over the last twelve years: a step line colored by employer, the same employer the same color in both, a dashed ghost of the full-time salary above what is paid while part time, and a callout at each change (the new employer, a change of hours, or the raise, with raises close together told as one); hovering a change shows its detail; choosing a stretch of the line (by pointer or keyboard) shows its row under the chart, with what the paychecks say about it and a correction; and each chart's + button opens a pay change for that person in a dialog, filled in from the job in force. A status card counts the runs that disagree and opens the Jobs page, which lists them above the charts, each with the change its paychecks suggest (a run well under the salary suggests the same salary at a share of full time).

## Receipts from email

Some stores email a receipt for every purchase. `exporter/` is a separate, small Apps Script (one file, `Code.js`) that copies new receipts into the Drive inbox once a day, as one text file per run (`receipts_<time>.txt`). It runs only the searches the household's settings allow: per store, mail from the addresses in `receipt_sender:<store>` and, if `receipt_subject:<store>` is set, whose subject has one of its phrases (separated by `|`). The settings live in the ledger and are edited in the views' Settings tab like any other, so no store is named in the repo or the script. The exporter builds each Gmail search itself from those plain addresses and words (`from:(a OR b) subject:("x" OR "y")`), and both the settings check and the exporter refuse anything else, so no setting can widen a search past its senders. It holds the only Gmail permission in the system, read-only, and never changes Gmail. That permission, `gmail.readonly`, covers the whole mailbox: Gmail has no narrower scope that still shows a message's body, so the searches limit what the exporter reads, not what it could read. What it reads can go nowhere but its own Drive files: it has no network access and cannot send mail, and a test holds its permissions to Gmail read-only, its own files and its trigger. It gets its searches without any other access: it makes one empty file in its folder, compute writes the searches into that file's description (`inbox.write_receipt_searches`; ingest passes over the file), and the exporter reads them back, which `drive.file` allows for a file it made. It trusts the file only where it left it, in its own folder, and only as last changed by the account it runs as (compute runs as the same owner): if someone else who can edit the folder changes the file, or it is moved, the run stops and says so rather than reading their senders. Keep the household folder's sharing to the people who keep the books. If the file holds no searches the run fails, and Apps Script emails the failure, rather than quietly exporting nothing. A new search reaches the exporter after the next compute. The boundary is the script itself, one short file to read in full before pushing it. A message it can't read is kept and fetched again by its id on every run until it reads, however far the search window has moved on, and the first time it fails the run's file notes it, so ingest's notes and the status page show the Gmail id and the error. Two exceptions, each logged in the exporter's run: a message deleted from Gmail since is no longer tried, and past 200 unreadable messages the oldest are dropped (by then the status page will have shown each one). `installTrigger` replaces only its own trigger. `exporter/test` runs it in CI against a fake Gmail and Drive. Its Drive permission is `drive.file`, which reaches only what the exporter itself created: it makes a folder of its own, `email_receipts`, on its first run, and you move that folder into the inbox once. The engine reads the inbox and the folders directly inside it. The engine keeps its Sheets and Drive access only and reads the file like any other export: `parsers/email_receipts.py` recognizes each receipt layout by its body and reads it item by item into `order_items` (one order per receipt, keyed by the message id, so a receipt exported twice is read once). A layout with no reader yet is counted in the ingest notes and left for later.

The first layout is a co-op's point-of-sale receipt (service `co_op`), which marks each item's tax class, so food, alcohol, toys and games and everything else (candles, medicine) separate, and tax and coupons are shared out so the items add to the charge. The household names the store's card lines with a ledger parameter, jurisdiction `household`, key `order_payee:co_op`, value a pattern for the payee; any store with an order history can be added the same way (`explain.order_services`), and its charges then split by what was bought like Amazon's.

The second is a bookseller's (service `bookseller`, key `order_payee:bookseller`): the receipt it emails from the register when you ask for one, read item by item at what each came to after member discounts and rewards, with the tax shared out. Toys, games and puzzles go to toys and games (family) and everything else to books (media). Its online billing summaries name the items but not their prices, so one that bills a single item reads as that item, and one that bills several is counted in the notes and stays one charge. Some stores put HTML in a receipt's plain-text part; the exporter and the reader both turn that into text.

App stores email a receipt for every purchase and renewal, so they are read the same way instead of from a data download. Apple's receipts (service `apple`, two layouts: the older one, printed twice, which is read once, and the newer one with Billing and Payment) are read item by item with the tax shared out; Google Play's (service `google`) are read one order at a time at what was charged, keyed as the Takeout reader keys a transaction, so a purchase in both is read once. Neither is categorized by department: like Google's purchase list, each card line (`APPLE.COM/BILL`, `GOOGLE *...`) is named after what its order bought, the app first (`explain.match_named`), so review asks once about a subscription and every renewal follows the answer. An Apple line is asked about as APPLE and its app (APPLE ONE, APPLE ICLOUD, APPLE TV for every rental), with what it bought beside the bank's payee; an Apple Card offer above a newer receipt's items is skipped, and an item read with the offer as its app is repaired when matched. A receipt in one of these layouts that doesn't add up is left out with its id in the ingest notes, never refusing the rest of the file. Add their senders as settings, for example `receipt_sender:apple` = `no_reply@email.apple.com` with `receipt_subject:apple` = `receipt`, and `receipt_sender:google` = `googleplay-noreply@google.com` with `receipt_subject:google` = `Order Receipt | updated your subscription`; to read receipts from before the exporter's next search, set its `SINCE` property back once (`2025/07/01`, say): receipts already read are read once.

Two more stores read the same way. A farm store's register receipts (service `farm_store`, key `order_payee:farm_store`) are read item by item at the price after any discount, with the tax shared over the taxed items: an untaxed item is food and a donation is charity. An outfitter's (service `outfitter`, key `order_payee:outfitter`) come as store eReceipts and online order confirmations; member rewards used are shared out of a store sale by amount, while an online order is charged as each part ships, so its rewards come off the first items and each item reads at what its part cost the card. A charge matches a shipment, an order or, for a store that charges each part of a shipment on its own, one item of it (`explain.order_groups`). Their charges then split by what was bought, like Amazon's; the items an outfitter's receipt names carry no department, so they fall to household until a person sets an item's category. Some of these receipts print one line per HTML block (`<pre>`); the exporter keeps those lines.

PayPal's emails replace its activity download (the QIF still reads): each payment's receipt, in the merchant's layout or PayPal's own, each refund and each payment a person sends goes to `payment_details` as the download's rows do, keyed by PayPal's transaction id so a receipt and its authorization are one payment, and a PAYPAL line on a card takes its counterparty as its payee. A transfer out to the bank is not a payment, and the search below leaves it out.

Venmo's emails read the same way (service `venmo`): each payment sent or received, with its note, names the VENMO line it matches, and each transfer to the bank names its cash-out line after the payments received since the transfer before it ("Venmo transfer: partner (Concert tickets); sam"). Venmo emails only the account's owner, so a second person's payments come in only if their Venmo emails are forwarded to the mailbox the exporter reads; Gmail's forwarding keeps Venmo as the sender. Settings like `receipt_sender:venmo` = `venmo@venmo.com` with `receipt_subject:venmo` = `paid | transfer`.

For the three: `receipt_sender` set to the farm store's eReceipt address; the outfitter's notices address with `receipt_subject` `eReceipt | Thanks for your order` (not its shipping notices); and `service@paypal.com` with `receipt_subject` `USD | receipt | refund` (not its transfer notices, activity reports or security notices).

To set it up (`npm i -g @google/clasp`, logged in):

1. `cd exporter && clasp create-script --type standalone --title "Household receipt exporter" --rootDir .`, then `git checkout -- appsscript.json` (creating the project writes a default manifest over the repo's, which has the permissions and services the script needs), then `clasp push`
2. Run `exportReceipts` once. It asks for Gmail read access and access to its own Drive files, makes `email_receipts` in My Drive with its empty searches file inside, and stops: there are no searches yet
3. Move `email_receipts` into the household inbox folder
4. Add a `receipt_sender:<store>` setting per store in the views (and a `receipt_subject:<store>` where a sender also emails things that aren't receipts), then run ingest and compute, which writes them into the searches file
5. Run `exportReceipts` again: it exports every receipt so far. Then run `installTrigger` once to run it every morning

## The weekly email

The engine runs when you run it, so nothing else would tell you the books need attention. `nudge/` is a separate, small Apps Script (one file, `Code.js`) that sends one email on Saturday mornings listing what needs doing, grouped by what to do, or no email when nothing does. It only ever mentions things you can act on:

- **Stale for a month**: a download whose history ends more than 30 days ago (or never downloaded, with lines waiting for it); review questions whose oldest line is more than 30 days old; files that have sat in the inbox for 30 days (a file the last ingest refused is listed with the reason); an ingest more than 30 days old that compute never followed.
- **Tax, within 30 days of the deadline**: withholding projected to miss `target_refund` by more than `withholding_tolerance` (default 500), with the extra per paycheck that fixes it, in the 30 days before the year's last paycheck; a 401(k) contribution (elective or after-tax) on pace to miss or pass its limit, in the same window. These are the levers the household controls: the W-4, the WT-4, the supplemental rate for vests and bonuses, and 401(k) contributions.
- **FSA money left from last year**: every week from January 1, until it is claimed or the claim deadline passes.
- **A setting that can't be used**: a link that isn't https, a deadline that isn't a date.

Compute decides what is due and when (`nudges.py`) and publishes it to Reports as `nudges`: each item with its group, words, link and the dates between which it belongs in the email (`show_from`, `show_until`). The script keeps the rows whose dates include the day it runs, so a Reports table a few weeks old still gives the right email. It adds the three things only it can see live: inbox files (the last ingest records the inbox's folder in `run_log`, so there is nothing to set up), files ingest refused, and Reports behind the ledger. If it can't read Reports or list the inbox, the email says so rather than skipping a week.

FSA balances (`fsa_balances` in Reports) come from the pay stubs and the reimbursement deposits. A plan year's election is its deductions (the year-to-date on each person's last stub that year, plus the deductions still to come for the year in progress). A reimbursement is a deposit from the administrator (`fsa_payee_pattern`) in one of the categories each account pays (`lpfsa_categories`, `dcfsa_categories`). These are the categories you already give those deposits in Review, since one administrator pays both accounts. A deposit between January 1 and last year's claim deadline pays off last year's money first; a note such as `fsa 2026` on the transaction puts it in that plan year instead. The claim deadlines are `lpfsa_claim_deadline` and `dcfsa_claim_deadline`, each `MM-DD` of the year after the plan year, or `lpfsa_claim_deadline:2026` with a full date for one plan year. An unset deadline is taken as March 31, and the email says so.

The links and deadlines are household settings in the ledger (`settings.py`), changed in the views' Settings tab like any other edit, so neither the script nor the repo holds any of them: `views_url` (links open the right page, such as `?view=edit&tab=review`), `payroll_url`, `benefits_url` and `fsa_claims_url`. The Settings tab lists every known setting, set or not, with what it is for. The script's permissions are Reports read-only, Drive file names and dates (never contents), sending mail to you, and its own trigger. `nudge/test` runs it in CI against faked Sheets, Drive and mail.

To set it up (`npm i -g @google/clasp`, logged in):

1. `cd nudge && clasp create-script --type standalone --title "Household weekly email" --rootDir .`, then `git checkout -- appsscript.json` (creating the project writes a default manifest over the repo's, which has the permissions and services the script needs), then `clasp push`
2. In the script editor, Project Settings, Script properties: `REPORTS_ID`, the same id the views use
3. Run `preview` once. It asks for its permissions, then logs the email it would send today
4. Run `installTrigger` once to send it every Saturday at 7 in the morning
5. In the views' Settings tab, set the links and the FSA settings

## Views

Compute writes each view's data as a Reports table, and `web/` draws it: a TypeScript Apps Script web app that reads Reports under the viewer's own Google sign-in and draws with Google Charts. It opens on a status page, in Material 3 (light or dark with the system): the latest ingest and compute, from `run_log` (each stage's summary, as JSON) and `run_notes` (every line each printed), with a card for each thing that needs you (lines open in review, downloads due, balances or tax lines that disagree, unexplained withholding, inbox files not read, transfers with no partner, saved changes ingest refused). A card says what it counts in words and lists the things themselves where Reports has them (each download due from `coverage`, with how far it reaches and how many lines wait for it; how the review questions split from `editor_review`), with a button to the Edit tab that answers it. Below them, how lines since `REVIEW_FROM` were categorized (your answers, receipts and order histories, payee rules, transfers, the model, and what still waits), the tax projection as bars from zero (a refund left, an amount owed right), and both runs' full logs, open, with the lines behind each card marked; it says so when compute hasn't run since the last ingest. The next view is the `flows` table (`flows.py`) as a Sankey: pay through taxes, deductions and net pay into the accounts (vested shares go straight to savings), then out to savings and each category (savings categories also flow back in, as shares sold; a category that got more back than it spent shows as money back; whatever the period didn't cover came from or went to cash balances), for any month, any year, or a year's monthly average (the year divided by the months it has data for), by category or by group, each node labeled with its total. Shares sold count as income only for what the sale made or lost against their value when they vested, which was already counted as pay: each period's net gain on sales (`equity_sales`, by sale date) flows from "capital gains" into savings, and a net loss from savings to "capital losses"; the proceeds reaching the bank come from savings. Under the chart, the same money by what it is to the household, in four columns: income (pay with vested shares at their value, other income, and the net gain on shares sold, or the net loss as a negative line), other money in (shares sold and other money drawn from savings, money back, cash already in the accounts), taxes and deductions, and where it went (each category, savings, vested shares, cash left in the accounts), each with its total and a bar per line, and the stops on the way (net pay, accounts) in a line below (`shape.flowSummary`). A year takes each pay line's year-to-date amount from the year's last stub, so a missing stub doesn't shrink the year, and pay deposits no stub accounts for show as "pay without a stub (person)", matched to a person by their employer's name on the deposit. The Budget page has two tabs. Lines sets any month, quarter or calendar year beside any other of the same kind (quick picks for the one before and the same one a year earlier), from one book the page loads once (`getBudgetBook`: the targets in `budget_vs_actual`, `daily_actuals`, `subscription_months`) and shapes itself with `web/src/budgetview.ts`, which the build inlines into the page, so a new lens or comparison asks the server nothing. Lines are grouped, each with where its target comes from, its budget for the whole period, what was spent, a bar (red past the budget, marked where it ends), the other period's spending and the change; tracked recurring charges sit under their line. While a period is not over, "Same weeks only" sets its spending so far beside the other period's over as many days from its start. Choosing a line opens a drawer with its twelve months against its target, its transactions (a charge an order history explains lists its items, a split part is marked, and its id opens its own page), and its budget line to change from a date, end, schedule an amount on, or set to `recurring`, with its charges and allowance added up as you type. Recurring is the tab described above. Transfers and income are left out. `web/src/shape.ts` turns rows into chart and table data and `web/src/edits.ts` builds change sets; both are tested under Node. `web/test/browser` drives the built page in Chromium with the server calls faked, each answer held back at will, to test what a person meets: a change made while Save runs stays for the next save, a failed save keeps every change and the next Save checks whether it landed, a past year's tax page has no scenario to choose, and a load that fails says so (`npm run test:browser` after `npm run build`; CI runs it). `web/test/server` runs the built server code under Node with Apps Script's services faked, the user property store holding to its limits (9 KB a value, 500 KB in all): each saved change set keeps its own small record (its edits in words, as many as fit, and how many more), the oldest past 40 are dropped and filed ones tidied, and once the file is in Drive a save never reports failure (a record that can't be kept comes back as a warning); the same request saved twice writes one file, found again by its request after ingest has moved it. Change sets carry their time to the millisecond, one person's are strictly in order, and each file name ends in a short unique suffix. A tab that doesn't exist yet reads as empty, but any other failure to read Reports is reported, never shown as empty data. No IDs or data live in `web/`.

### Taxes

The Taxes view is this year's return worked out from the pay stubs, vests, sales and your estimates (`projection.py`), and a status card links to it:
- **Both returns line by line.** Form 1040 from wages to the refund or amount owed, the Schedule A, D and 2 lines it uses, and Wisconsin Form 1 from Wisconsin income to the balance (`tax_lines` in Reports), as things stand. Wisconsin's line numbers come from the blank Form 1 on file and are cited like tax law (`taxdata.FORM_LINES`, checked by `tools/verify_tax_law.py`); a year whose form isn't on file yet uses the latest form's numbers, and the page says so. This year's scenarios (no extra withholding, vests at 22%, stock 20% higher or lower) are compared by their totals in a panel of their own; the forms never change with them, and rows for any other scenario an older compute left in `tax_lines` are ignored.
- **Taxes over the years.** The Taxes page opens with a column per filed year (`taxhistory.py`, the `tax_history` table), built from `return_facts` alone so a year shows as soon as its return's figures are in, whether or not its tax law is on file. A switch splits each year's income where it went (federal and state income taxes after credits, the credits as a hatched part of what was kept, and what was kept; a year's `refundable_credits`, such as 2021's child and dependent care credits, count as credits and come off the federal income tax), where it came from (wages by person, interest and dividends, capital gains, other income; a capital loss below the line at the most the return deducts) or how it was taxed (taxable income and what was deducted); another shows dollars or shares of the whole; a third picks the federal return or the state ones, a year's state returns side by side (a year in two states has a part-year return for each). Hovering a column gives each part and its change on the year before, and clicking a year the page has opens it below. `tax_check` recomputes only the years whose tax law is on file (`taxdata.PARAMS`); an older year is shown as filed, and the compute log says so.
- **Last year as filed.** Once last year's return is in `return_facts`, the page lays out the returns you filed (Form 1040, then Wisconsin Form 1 or, for a part-year resident, Form 1NPR, and PA-40 when there is one), each line computed from the return's own figures (the W-2s and the rest, the same computation `tax_check` compares) beside the line you filed, with what's off (`projection.as_filed`). Until then it works out last year from its stubs, with no scenarios.
- **A job goes on until a new one is recorded.** Each job is projected to December 31, however long since its last stub, until `comp_events` has a row for that person at another employer; from that date nothing more is projected for it, and the page notes it (`projection.job_ends`). A year that is over is its stubs alone.
- **Withholding for the rest of the year.** For each return, the W-4 Step 4(c) or WT-4 additional amount per paycheck that lands the year on a refund of `target_refund` (a household setting, 2,000 unless set), on no balance, and on owing that much, from the year so far plus the projection with future vests withheld at `planned_supplemental_rate` (35% unless set), on the paychecks of whoever has the most left (`withholding_plan`). A target withholding can't reach says how close it gets, and a federal balance owed says whether it escapes the underpayment penalty (owing under 1,000, or withholding at least the smaller of 90% of this year's tax and last year's safe harbor; Pub 505, cited).
- **Retirement and health accounts.** The 401(k), the mega backdoor Roth (after-tax 401(k) contributions against what 415(c) leaves, marked converted when the household setting `after_tax_401k_converts_to_roth` is TRUE, since a stub can't show a conversion), the HSA, a limited-purpose or health FSA (against the year's health FSA limit, per person and employer) and the dependent-care FSA, each so far this year and by December 31 against its limit (`elections`). A backdoor Roth IRA isn't on a pay stub, so it shows as not tracked.

### Editing in the views

The Edit view changes the ledger without opening it: answering review questions (a merchant, or one line, which can be split; a merchant's question can also be split into its lines, each answered on its own; once every line has an answer the question leaves the list), payee rules (change or stop), categories and old names, household settings, withholding explanations and possible duplicates. Budget lines (change from a date, end, or schedule a one-off amount; an amount on a date that has one replaces it, and says what it replaced) and recurring charges are changed on the Budget page, and jobs and pay changes (`comp_events`) on the Jobs page; their edits wait in the same bar. Each tab is a list on the left, one row per item with a line about it and a count and filter at the top, and the chosen item's editor on the right (on a phone, the editor replaces the list). A transaction's id in the budget drill-down opens its own page: what it bought, each item with its category to change (kept with the item in the ledger's `item_categories`, so the line, split by its items, follows once ingest and compute run, and the split editor below previews it at once), one category for it (or for every line from its merchant), a split editor that adds the parts up against the line as you type (or splits it by what an order history says it bought), its note and one-off flag, or drop it as a duplicate. Edits stay in the page, listed in a bar at the bottom, until Save; leaving with unsaved edits asks first.

The views still never write the ledger. Save writes one change set, `changes_<time>Z.json`, into the views' own Drive folder, and ingest, the only writer of the ledger, reads it from the inbox (`parsers/changes.py`). Each edit becomes the one row a person would have typed (`proposal_decisions`, `txn_corrections`, `budget_rules`, `payee_rules`, `categories`, `category_aliases`, `parameters`), recorded at the time it was saved, and each is logged as ingest writes it. The views' Drive permission is `drive.file`, so they reach only files they made: the first Save makes a folder `web_edits` in My Drive, and you move it into the household inbox once, as with `email_receipts`. The Saved tab, and a card on the status page, list change sets ingest hasn't read yet. Each Save carries an id the browser made for it, kept on the file in Drive: the same id saved again answers with the file it already wrote. When a Save fails, its answer may have been lost after Drive had the file, so the next Save first asks whether that request landed (`findSave`, which waits for a Save still running) and writes nothing twice. A file it finds in the trash reads as discarded, never as saved, and the changes stay for the next Save. Discard all never drops what a save may have written: while a save or that check runs, Save and Discard all wait, and an edit sent in a save that hasn't answered can't be undone. After a save that didn't confirm, Discard all first checks it; if it landed, its changes are saved, and the page offers to discard that change set too (`discardWaiting`). Discarding puts the file in the trash, so no ingest from then on reads it; an ingest already running may have downloaded it first and still apply it, and nothing in Drive can stop that. So the views remember each discard for thirty days, and when the ledger holds a discarded change set, the status page says it was applied anyway, with its edits, so the settings can be edited back. The ledger is the record here, not the run_log: each ingest publishes `changes_written` to Reports from `source_documents` (the last 45 days), so a later run can't hide one, and one whose rows were written but whose filing in Drive failed is there too (the run_log marks those `written` as well). It matches by Drive file id, not name. Ingest writes all of a run's ledger rows, each file's `source_documents` row with them, in one atomic Sheets write (`sheets.append_tables`): a failure leaves the ledger as it was, so a change set's edits can't land without the record of them. A discard the views can't remember says so, rather than promising the status page will tell. Leaving the page warns while a save is unanswered. A change set saved before the last ingest that the ingest never listed is marked as unseen, on the status page and in the Saved tab: ingest reads only the inbox and the folders directly in it, so `web_edits` is still in My Drive.

A change set fails closed. It is strict JSON in a declared format and version, with no unknown fields, size and count limits, and rows written as text (never formulas). Every value is checked alone (dates, enums, patterns that compile and stay short, splits that read), then against the ledger (categories and old names that exist, transactions and stubs that exist, splits that add up to the line). An edit that replaces a setting carries the fields of the row it replaced (`was`), a scheduled amount included, since the budget keeps the last amount on a date (`editor_scheduled` in Reports lists those in force); if the ledger has moved on since (another change set, or a seed), the edit is stale. One change set edits each setting once, by the same target the editor stages by (`editTarget`; a scheduled amount is one per line and date, a pair of lines one pair either way round). One bad or stale edit refuses the whole file, which stays in the inbox with every reason, shown on the status page and in the Saved tab, where Discard moves it to the trash. Compute publishes what the editors show as `editor_*` tables in Reports: each setting's row in force, each budget line in words with this month's target and the last twelve months' spending, and the review queue. Accounts, loans, pay history and allocation targets still arrive as seed files.

## Tax law

Federal and state rates, limits and withholding tables live in `src/household/taxdata.py`; each state's return and withholding method is in a module of its own. Every value cites the page of a source document that states it (`CITATIONS`), and each source is pinned by the SHA-256 of the PDF it was checked against (`DOCUMENTS`). The `tax_sources` report lists every value with its citation and a link to the PDF in the record store.

A release that changes tax law (each January) adds the new year's values and citations, then checks them against the PDFs:

```
python tools/verify_tax_law.py <folder of source PDFs>
```

It checks that each quote is on its cited page and states the value the code uses, that every bracket threshold appears, and that every row of Pub 15-T's annual married-filing-jointly table equals the brackets shifted by the table floor. Where a state prints no rate schedule or deduction formula, those are proved by reproducing every row of its printed tables and the amounts in its worksheets. It exits nonzero on any failure, missing document, or uncited value.

## Before pushing

This repo is public, so hooks check for household data before it can leave the machine. Binary files (PDFs, images, office files, archives) are refused outright unless `tests/fixtures/BINARIES` lists them as made-up fixtures, and a listed PDF's text is checked like any other file: real statements and exports are binary, and line checks can't see inside them. Turn them on once per clone with `git config core.hooksPath .githooks`. The pre-commit and commit-msg hooks run the text checks below on the staged changes and the message (`push_guard.py --staged`, `--message`), so a value is caught before it is in a commit; the pre-push hook runs everything again as the backstop. `tools/push_guard.py` checks every added line and commit message against the leak guard's patterns and against a private denylist of the household's real values (names, places, employers, account digits, and every amount with cents in the pay stubs and transactions, however it is written), kept outside the repo at `~/.config/household/denylist.txt`; then it runs the import guard and the tests. `tools/denylist.py` builds the denylist from ledger exports and a words file, and adds every category in a personal group (`personal`, `family_support`), since those are named for people. Examples and tests use made-up names and categories only (CLAUDE.md lists them); a GitHub address is not checked, since it is public. Without a denylist the push stops (`HOUSEHOLD_NO_DENYLIST=1` skips that check; `HOUSEHOLD_PUSH_QUICK=1` skips the tests).

## Releases

Notebooks pin a tag, for example `pip install git+https://github.com/lewis-john-lloyd/household@v0.0.1`. Upgrading is a deliberate edit of that tag; rolling back is reverting it.

Ordinary commits leave the version number alone. When work is ready to run, one release commit sets the version in `pyproject.toml` and `household/__init__.py`, and the owner tags that commit.
