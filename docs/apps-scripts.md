# Receipts, the weekly email and the county check

The small Apps Scripts that run beside the engine.

## Receipts from email

Some stores email a receipt for every purchase. `exporter/` is a separate, small Apps Script (one file, `Code.js`) that copies new receipts into the Drive inbox once a day, as one text file per run (`receipts_<time>.txt`). It runs only the searches the household's settings allow: per store, mail from the addresses in `receipt_sender:<store>` and, if `receipt_subject:<store>` is set, whose subject has one of its phrases (separated by `|`). The settings live in the ledger and are edited in the views' Settings tab like any other, so no store is named in the repo or the script. The exporter builds each Gmail search itself from those plain addresses and words (`from:(a OR b) subject:("x" OR "y")`), and both the settings check and the exporter refuse anything else, so no setting can widen a search past its senders.

It holds the only Gmail permission in the system, read-only, and never changes Gmail. That permission, `gmail.readonly`, covers the whole mailbox: Gmail has no narrower scope that still shows a message's body, so the searches limit what the exporter reads, not what it could read. What it reads can go nowhere but its own Drive files: it has no network access and cannot send mail, and a test holds its permissions to Gmail read-only, its own files and its trigger. It gets its searches without any other access: it makes one empty file in its folder, compute writes the searches into that file's description (`inbox.write_receipt_searches`; ingest passes over the file), and the exporter reads them back, which `drive.file` allows for a file it made.

It trusts the file only where it left it, in its own folder, and only as last changed by the account it runs as (compute runs as the same owner): if someone else who can edit the folder changes the file, or it is moved, the run stops and says so rather than reading their senders. Keep the household folder's sharing to the people who keep the books. If the file holds no searches the run fails, and Apps Script emails the failure, rather than quietly exporting nothing. A new search reaches the exporter after the next compute. The boundary is the script itself, one short file to read in full before pushing it. A message it can't read is kept and fetched again by its id on every run until it reads, however far the search window has moved on, and the first time it fails the run's file notes it, so ingest's notes and the status page show the Gmail id and the error.

Two exceptions, each logged in the exporter's run: a message deleted from Gmail since is no longer tried, and past 200 unreadable messages the oldest are dropped (by then the status page will have shown each one). `installTrigger` replaces only its own trigger. `exporter/test` runs it in CI against a fake Gmail and Drive. Its Drive permission is `drive.file`, which reaches only what the exporter itself created: it makes a folder of its own, `email_receipts`, on its first run, and you move that folder into the inbox once. The engine reads the inbox and the folders directly inside it. The engine keeps its Sheets and Drive access only and reads the file like any other export: `parsers/email_receipts.py` recognizes each receipt layout by its body and reads it item by item into `order_items` (one order per receipt, keyed by the message id, so a receipt exported twice is read once). A layout with no reader yet is counted in the ingest notes and left for later.

The first layout is a co-op's point-of-sale receipt (service `co_op`), which marks each item's tax class, so food, alcohol, toys and games and everything else (candles, medicine) separate, and tax and coupons are shared out so the items add to the charge. The household names the store's card lines with a ledger parameter, jurisdiction `household`, key `order_payee:co_op`, value a pattern for the payee; any store with an order history can be added the same way (`explain.order_services`), and its charges then split by what was bought like Amazon's.

The second is a bookseller's (service `bookseller`, key `order_payee:bookseller`): the receipt it emails from the register when you ask for one, read item by item at what each came to after member discounts and rewards, with the tax shared out. Toys, games and puzzles go to toys and games (family) and everything else to books (media). Its online billing summaries name the items but not their prices, so one that bills a single item reads as that item, and one that bills several is counted in the notes and stays one charge. Some stores put HTML in a receipt's plain-text part; the exporter and the reader both turn that into text.

App stores email a receipt for every purchase and renewal, so they are read the same way instead of from a data download. Apple's receipts (service `apple`, two layouts: the older one, printed twice, which is read once, and the newer one with Billing and Payment) are read item by item with the tax shared out; Google Play's (service `google`) are read one order at a time at what was charged, keyed as the Takeout reader keys a transaction, so a purchase in both is read once. Neither is categorized by department: like Google's purchase list, each card line (`APPLE.COM/BILL`, `GOOGLE *...`) is named after what its order bought, the app first (`explain.match_named`), so review asks once about a subscription and every renewal follows the answer.

An Apple line is asked about as APPLE and its app (APPLE ONE, APPLE ICLOUD, APPLE TV for every rental), with what it bought beside the bank's payee; an Apple Card offer above a newer receipt's items is skipped, and an item read with the offer as its app is repaired when matched. A receipt in one of these layouts that doesn't add up is left out with its id in the ingest notes, never refusing the rest of the file. Add their senders as settings, for example `receipt_sender:apple` = `no_reply@email.apple.com` with `receipt_subject:apple` = `receipt`, and `receipt_sender:google` = `googleplay-noreply@google.com` with `receipt_subject:google` = `Order Receipt | updated your subscription`; to read receipts from before the exporter's next search, set its `SINCE` property back once (`2025/07/01`, say): receipts already read are read once.

Two more stores read the same way. A farm store's register receipts (service `farm_store`, key `order_payee:farm_store`) are read item by item at the price after any discount, with the tax shared over the taxed items: an untaxed item is food and a donation is charity. An outfitter's (service `outfitter`, key `order_payee:outfitter`) come as store eReceipts and online order confirmations; member rewards used are shared out of a store sale by amount, while an online order is charged as each part ships, so its rewards come off the first items and each item reads at what its part cost the card. A charge matches a shipment, an order or, for a store that charges each part of a shipment on its own, one item of it (`explain.order_groups`). Their charges then split by what was bought, like Amazon's; the items an outfitter's receipt names carry no department, so they fall to household until a person sets an item's category. Some of these receipts print one line per HTML block (`<pre>`); the exporter keeps those lines.

PayPal's emails replace its activity download (the QIF still reads): each payment's receipt, in the merchant's layout or PayPal's own, each refund and each payment a person sends goes to `payment_details` as the download's rows do, keyed by PayPal's transaction id so a receipt and its authorization are one payment, and a PAYPAL line on a card takes its counterparty as its payee. A transfer out to the bank is not a payment, and the search below leaves it out.

Venmo's emails read the same way (service `venmo`): each payment sent or received, with its note, names the VENMO line it matches, and each transfer to the bank names its cash-out line after the payments received since the transfer before it ("Venmo transfer: partner (Concert tickets); sam"). Venmo emails only the account's owner, so a second person's payments come in only if their Venmo emails are forwarded to the mailbox the exporter reads; Gmail's forwarding keeps Venmo as the sender. Settings like `receipt_sender:venmo` = `venmo@venmo.com` with `receipt_subject:venmo` = `paid | transfer`.

For the three: `receipt_sender` set to the farm store's eReceipt address; the outfitter's notices address with `receipt_subject` `eReceipt | Thanks for your order` (not its shipping notices); and `service@paypal.com` with `receipt_subject` `USD | receipt | refund` (not its transfer notices, activity reports or security notices).

To set it up (`npm i -g @google/clasp`, logged in):

1. `cd exporter && clasp create-script --type standalone --title "Household receipt exporter" --rootDir .`, then `git checkout -- appsscript.json` (creating the project writes a default manifest over the repo's, which has the permissions and services the script needs), then `clasp push`
2. Run `exportReceipts` once. It asks for Gmail read access and access to its own Drive files, makes `email_receipts` in My Drive with its empty searches file inside, and stops: there are no searches yet
3. Move `email_receipts` into the household inbox folder
4. Add a `receipt_sender:<store>` setting per store in the views (and a `receipt_subject:<store>` where a sender also emails things that aren't receipts), then run ingest and compute, which writes them into the searches file
5. Run `exportReceipts` again: it exports every receipt so far. Then run `installTrigger` once to run it every morning

## The weekly email

The engine runs when you run it, so nothing else would tell you the books need attention. `nudge/` is a separate, small Apps Script (one file, `Code.js`) that sends one email on Saturday mornings listing what needs doing, grouped by what to do, or no email when nothing does. It only ever mentions things you can act on:

- **Stale for a month**: a download whose history ends more than 30 days ago (or never downloaded, with lines waiting for it); review questions whose oldest line is more than 30 days old; files that have sat in the inbox for 30 days (a file the last ingest refused is listed with the reason); an ingest more than 30 days old that compute never followed.
- **Tax, within 30 days of the deadline**: withholding projected to miss `target_refund` by more than `withholding_tolerance` (default 500), with the extra per paycheck that fixes it, in the 30 days before the year's last paycheck; a 401(k) contribution (elective or after-tax) on pace to miss or pass its limit, in the same window. These are the levers the household controls: the W-4, the WT-4, the supplemental rate for vests and bonuses, and 401(k) contributions.
- **FSA money left from last year**: every week from January 1, until it is claimed or the claim deadline passes.
- **A setting that can't be used**: a link that isn't https, a deadline that isn't a date.

Compute decides what is due and when (`nudges.py`) and publishes it to Reports as `nudges`: each item with its group, words, link and the dates between which it belongs in the email (`show_from`, `show_until`). The script keeps the rows whose dates include the day it runs, so a Reports table a few weeks old still gives the right email. It adds the three things only it can see live: inbox files (the last ingest records the inbox's folder in `run_log`, so there is nothing to set up), files ingest refused, and Reports behind the ledger. If it can't read Reports or list the inbox, the email says so rather than skipping a week.

FSA balances (`fsa_balances` in Reports) come from the pay stubs and the reimbursement deposits. A plan year's election is its deductions (the year-to-date on each person's last stub that year, plus the deductions still to come for the year in progress). A reimbursement is a deposit from the administrator (`fsa_payee_pattern`) in one of the categories each account pays (`lpfsa_categories`, `dcfsa_categories`). These are the categories you already give those deposits in Review, since one administrator pays both accounts. A deposit between January 1 and last year's claim deadline pays off last year's money first; a note such as `fsa 2026` on the transaction puts it in that plan year instead. The claim deadlines are `lpfsa_claim_deadline` and `dcfsa_claim_deadline`, each `MM-DD` of the year after the plan year, or `lpfsa_claim_deadline:2026` with a full date for one plan year. An unset deadline is taken as March 31, and the email says so.

The links and deadlines are household settings in the ledger (`settings.py`), changed in the views' Settings tab like any other edit, so neither the script nor the repo holds any of them: `views_url` (links open the right page, such as `?view=edit&tab=review`), `payroll_url`, `benefits_url` and `fsa_claims_url`. The Settings tab lists every known setting, set or not, with what it is for. The script's permissions are Reports read-only, Drive file names and dates (never contents), sending mail to you, and its own trigger. `nudge/test` runs it in CI against faked Sheets, Drive and mail.

To set it up (`npm i -g @google/clasp`, logged in):

1. `cd nudge && clasp create-script --type standalone --title "Household weekly email" --rootDir .`, then `git checkout -- appsscript.json` (creating the project writes a default manifest over the repo's, which has the permissions and services the script needs), then `clasp push`
2. In the script editor, Project Settings, Script properties: `REPORTS_ID`, the same id the views use
3. Run `preview` once. It asks for its permissions, then logs the email it would send today
4. Run `installTrigger` once to send it every Saturday at 7 in the morning
5. In the views' Settings tab, set the links and the FSA settings

### The county check

`assessor/` is another small Apps Script (one file, `Code.js`) that reads each home's parcel page on Dane County's AccessDane on the 3rd of each month and drops what is new into the inbox: each year's assessment and the county's estimate of fair market value (`property_values`), and each tax bill with its mill rate, credits and specials (`property_taxes`). Ingest reads them like any seed file; the Home page lists the estimates and the bills, and estimates the coming bill from the latest assessment at the last bill's mill rate. Compute writes the parcels (each home owned today with a `parcel` in `properties`, from the year it was bought) into the description of the script's own parcels file, so nothing about the household lives in the script. Its permissions are its own Drive files, the network limited by its manifest to AccessDane, and its own trigger. `assessor/test` runs its parser in CI on a made-up page.

To set it up:

1. `cd assessor && clasp create-script --type standalone --title "Household county check" --rootDir .`, then `git checkout -- appsscript.json`, then `clasp push`
2. Run `monthly` once. It asks for its permissions and makes the `county_assessments` folder in My Drive, with its parcels file in it
3. Move that folder into the household inbox folder, then run compute (it fills the parcels file)
4. Run `monthly` again (it writes the first files), then `installTrigger` once
