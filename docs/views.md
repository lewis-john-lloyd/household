# Views

The web app that draws Reports and edits the ledger through change sets. Its pages, in the menu's order: Status, Jobs, Budget, Cashflow, Taxes, Home, Investments and Retirement.

Compute writes each view's data as a Reports table, and `web/` draws it: a TypeScript Apps Script web app that reads Reports under the viewer's own Google sign-in and draws with Google Charts. It opens on a status page, in Material 3 (light or dark with the system): the latest ingest and compute, from `run_log` (each stage's summary, as JSON) and `run_notes` (every line each printed), with a card for each thing that needs you (lines open in review, downloads due, balances or tax lines that disagree, unexplained withholding, inbox files not read, transfers with no partner, saved changes ingest refused). A card says what it counts in words and lists the things themselves where Reports has them (each download due from `coverage`, with how far it reaches and how many lines wait for it; how the review questions split from `editor_review`), with a button to the part of the views that answers it.

Below them, how lines since `REVIEW_FROM` were categorized (your answers, receipts and order histories, payee rules, transfers, the model, and what still waits), the tax projection as bars from zero (a refund left, an amount owed right), and both runs' full logs, open, with the lines behind each card marked; it says so when compute hasn't run since the last ingest. The next view is the `flows` table (`flows.py`) as a Sankey: pay through taxes, deductions and net pay into the accounts (vested shares go straight to savings), then out to savings and each category (savings categories also flow back in, as shares sold; a category that got more back than it spent shows as money back; whatever the period didn't cover came from or went to cash balances), for any month, any year, or a year's monthly average (the year divided by the months it has data for), by category or by group, each node labeled with its total.

Shares sold count as income only for what the sale made or lost against their value when they vested, which was already counted as pay: each period's net gain on sales (`equity_sales`, by sale date) flows from "capital gains" into savings, and a net loss from savings to "capital losses"; the proceeds reaching the bank come from savings. Under the chart, the same money by what it is to the household, in four columns: income (pay with vested shares at their value, other income, and the net gain on shares sold, or the net loss as a negative line), other money in (shares sold and other money drawn from savings, money back, cash already in the accounts), taxes and deductions, and where it went (each category, savings, vested shares, cash left in the accounts), each with its total and a bar per line, and the stops on the way (net pay, accounts) in a line below (`shape.flowSummary`).

A year takes each pay line's year-to-date amount from the year's last stub, so a missing stub doesn't shrink the year, and pay deposits no stub accounts for show as "pay without a stub (person)", matched to a person by their employer's name on the deposit. The Budget page has two tabs. Lines sets any month, quarter or calendar year beside any other of the same kind (quick picks for the one before and the same one a year earlier), from one book the page loads once (`getBudgetBook`: the targets in `budget_vs_actual`, `daily_actuals`, `subscription_months`) and shapes itself with `web/src/budgetview.ts`, which the build inlines into the page, so a new lens or comparison asks the server nothing. The page's own code is TypeScript in `web/src/page`, a module per page or part (cashflow, budget, the drawer, recurring, jobs, the pending changes, the editor's forms, transactions, investments, home, taxes, status, retirement, and `main`, which loads and switches views); `tsconfig.page.json` checks it strictly for the browser (DOM types) together with the server's modules, so each call to the server is typed by the `Code.ts` function it reaches (`ask` and `call` in `shell.ts`, the names in `google.d.ts`) and each page's data by the type that function returns. The build inlines the modules into `Index.html` in the order `web/scripts/copy.mjs` lists, since they share one script and `main` starts the page; `budgetview.js` and `edits.js` are inlined before them, so the page stages an edit under the same target (`editTarget`) that change sets use.

Lines are grouped, each with where its target comes from, its budget for the whole period, what was spent, a bar (red past the budget, marked where it ends), the other period's spending and the change; tracked recurring charges sit under their line. While a period is not over, "Same weeks only" sets its spending so far beside the other period's over as many days from its start. Choosing a line opens a drawer with its twelve months against its target, its transactions (a charge an order history explains lists its items, a split part is marked, and its id opens its own page), and its budget line to change from a date, end, schedule an amount on, or set to `recurring`, with its charges and allowance added up as you type.

Recurring is the tab described above. Transfers and income are left out. `web/src/shape.ts` turns rows into chart and table data and `web/src/edits.ts` builds change sets; both are tested under Node. `web/test/browser` drives the built page in Chromium with the server calls faked, each answer held back at will, to test what a person meets: a change made while Save runs stays for the next save, a failed save keeps every change and the next Save checks whether it landed, a past year's tax page has no scenario to choose, and a load that fails says so (`npm run test:browser` after `npm run build`; CI runs it). `web/test/server` runs the built server code under Node with Apps Script's services faked, the user property store holding to its limits (9 KB a value, 500 KB in all): each saved change set keeps its own small record (its edits in words, as many as fit, and how many more), the oldest past 40 are dropped and filed ones tidied, and once the file is in Drive a save never reports failure (a record that can't be kept comes back as a warning); the same request saved twice writes one file, found again by its request after ingest has moved it.

Change sets carry their time to the millisecond, one person's are strictly in order, and each file name ends in a short unique suffix. A tab that doesn't exist yet reads as empty, but any other failure to read Reports is reported, never shown as empty data. No IDs or data live in `web/`.

### Taxes

The Taxes view is this year's return worked out from the pay stubs, vests, sales and your estimates (`projection.py`), and a status card links to it:
- **Both returns line by line.** Form 1040 from wages to the refund or amount owed, the Schedule A, D and 2 lines it uses, and Wisconsin Form 1 from Wisconsin income to the balance (`tax_lines` in Reports), as things stand. Wisconsin's line numbers come from the blank Form 1 on file and are cited like tax law (`taxdata.FORM_LINES`, checked by `tools/verify_tax_law.py`); a year whose form isn't on file yet uses the latest form's numbers, and the page says so. This year's scenarios (no extra withholding, vests at 22%, stock 20% higher or lower) are compared by their totals in a panel of their own; the forms never change with them, and rows for any other scenario an older compute left in `tax_lines` are ignored.
- **Taxes over the years.** The Taxes page opens with a column per filed year (`taxhistory.py`, the `tax_history` table), built from `return_facts` alone so a year shows as soon as its return's figures are in, whether or not its tax law is on file. A switch splits each year's income where it went (federal and state income taxes after credits, the credits as a hatched part of what was kept, and what was kept; a year's `refundable_credits`, such as 2021's child and dependent care credits, count as credits and come off the federal income tax), where it came from (wages by person, interest and dividends, capital gains, other income; a capital loss below the line at the most the return deducts) or how it was taxed (taxable income and what was deducted); another shows dollars or shares of the whole; a third picks the federal return or the state ones, a year's state returns side by side (a year in two states has a part-year return for each). Hovering a column gives each part and its change on the year before, and clicking a year the page has opens it below. `tax_check` recomputes only the years whose tax law is on file (`taxdata.PARAMS`); an older year is shown as filed, and the compute log says so.
- **Last year as filed.** Once last year's return is in `return_facts`, the page lays out the returns you filed (Form 1040, then Wisconsin Form 1 or, for a part-year resident, Form 1NPR, and PA-40 when there is one), each line computed from the return's own figures (the W-2s and the rest, the same computation `tax_check` compares) beside the line you filed, with what's off (`projection.as_filed`). Until then it works out last year from its stubs, with no scenarios.
- **A job goes on until a new one is recorded.** Each job is projected to December 31, however long since its last stub, until `comp_events` has a row for that person at another employer; from that date nothing more is projected for it, and the page notes it (`projection.job_ends`). A year that is over is its stubs alone.
- **Withholding for the rest of the year.** For each return, the W-4 Step 4(c) or WT-4 additional amount per paycheck that lands the year on a refund of `target_refund` (a household setting, 2,000 unless set), on no balance, and on owing that much, from the year so far plus the projection with future vests withheld at `planned_supplemental_rate` (35% unless set), on the paychecks of whoever has the most left (`withholding_plan`). A target withholding can't reach says how close it gets, and a federal balance owed says whether it escapes the underpayment penalty (owing under 1,000, or withholding at least the smaller of 90% of this year's tax and last year's safe harbor; Pub 505, cited).
- **Form 8949.** Each year's sales as the form lays them out (the `form_8949` report from `lots.py`): Part I short-term and Part II long-term, columns (a) to (h), a wash sale's code W and its adjustment, a tag where the plan reported another basis for the shares, and each part's totals beside the return's Schedule D line 7 or 15 as filed. The box (A to F) comes from the 1099-B.
- **Retirement and health accounts.** The 401(k), the mega backdoor Roth (after-tax 401(k) contributions against what 415(c) leaves, marked converted when the household setting `after_tax_401k_converts_to_roth` is TRUE, since a stub can't show a conversion), the HSA, a limited-purpose or health FSA (against the year's health FSA limit, per person and employer) and the dependent-care FSA, each so far this year and by December 31 against its limit (`elections`). A backdoor Roth IRA isn't on a pay stub, so it shows as not tracked.

### Editing in the views

The views change the ledger without opening it. Each change is made on the page it is about:

- **Cashflow**, beside the flow chart and its table: review, payee rules, possible duplicates, and each transaction's own page.
- **Budget**: categories, budget lines and recurring charges.
- **Taxes**: withholding explanations.
- **Jobs**: jobs and pay changes (`comp_events`).
- **Status**: household settings, and the change sets saved but not yet read.

A link to `?view=edit&tab=<part>` still opens a part where it now lives.

What can be changed:

- **Review questions**: answer a merchant, or one line, which can be split. A merchant's question can also be split into its lines, each answered on its own; once every line has an answer the question leaves the list.
- **Payee rules** (change or stop), **categories** and **old category names**, **household settings**, **withholding explanations** and **possible duplicates**.
- **Budget lines**: change from a date, end, or schedule a one-off amount. An amount on a date that has one replaces it, and says what it replaced.
- **A transaction's own page**, opened from its id in the budget drill-down: what it bought, each item with its category to change (kept with the item in the ledger's `item_categories`, so the line, split by its items, follows once ingest and compute run, and the split editor previews it at once); one category for it, or for every line from its merchant; a split editor that adds the parts up against the line as you type, or splits it by what an order history says it bought; its note and one-off flag; or drop it as a duplicate.

Each tab is a list on the left, one row per item with a line about it and a count and filter at the top, and the chosen item's editor on the right; on a phone, the editor replaces the list. Edits stay in the page, listed in a bar at the bottom, until Save. Leaving with unsaved edits asks first.

#### How an edit reaches the ledger

The views never write the ledger. Save writes one change set, `changes_<time>Z.json`, into the views' own Drive folder, and ingest, the only writer of the ledger, reads it from the inbox (`parsers/changes.py`). Each edit becomes the one row a person would have typed (`proposal_decisions`, `txn_corrections`, `budget_rules`, `payee_rules`, `categories`, `category_aliases`, `parameters`), recorded at the time it was saved, and each is logged as ingest writes it. Compute then publishes what the editors show as `editor_*` tables in Reports: each setting's row in force, each budget line in words with this month's target and the last twelve months' spending, and the review queue. Accounts, loans, pay history and allocation targets still arrive as seed files.

The views' Drive permission is `drive.file`, so they reach only files they made. The first Save makes a folder `web_edits` in My Drive; move it into the household inbox once, as with `email_receipts`. Ingest reads only the inbox and the folders directly in it, so a change set saved before the last ingest that the ingest never listed is marked as unseen, on the status page and in the Saved tab: `web_edits` is still in My Drive.

#### Saving safely

A save can fail halfway, or be discarded while an ingest is reading it. The views handle each case so nothing is written twice or lost:

- **Each Save carries an id** the browser made for it, kept on the file in Drive: the same id saved again answers with the file it already wrote.
- **A failed Save is checked before the next one.** Its answer may have been lost after Drive had the file, so the next Save first asks whether that request landed (`findSave`, which waits for a Save still running) and writes nothing twice. A file it finds in the trash reads as discarded, never as saved, and the changes stay for the next Save.
- **Discard all never drops what a save may have written.** While a save or that check runs, Save and Discard all wait, and an edit sent in a save that hasn't answered can't be undone. After a save that didn't confirm, Discard all first checks it; if it landed, its changes are saved, and the page offers to discard that change set too (`discardWaiting`).
- **A discard can lose a race with ingest.** Discarding puts the file in the trash, so no ingest from then on reads it, but an ingest already running may have downloaded it first and still apply it; nothing in Drive can stop that. So the views remember each discard for thirty days, and when the ledger holds a discarded change set, the status page says it was applied anyway, with its edits, so the settings can be edited back. A discard the views can't remember says so, rather than promising the status page will tell.
- **The ledger is the record, not the run log.** Each ingest publishes `changes_written` to Reports from `source_documents` (the last 45 days), matched by Drive file id, not name, so a later run can't hide one. One whose rows were written but whose filing in Drive failed is there too (the run log marks those `written` as well).
- **A run's rows land together.** Ingest writes all of a run's ledger rows, each file's `source_documents` row with them, in one atomic Sheets write (`sheets.append_tables`): a failure leaves the ledger as it was, so a change set's edits can't land without the record of them.
- Leaving the page warns while a save is unanswered.

#### What a change set must pass

A change set fails closed:

- It is strict JSON in a declared format and version, with no unknown fields, size and count limits, and rows written as text (never formulas).
- Every value is checked alone (dates, enums, patterns that compile and stay short, splits that read), then against the ledger (categories and old names that exist, transactions and stubs that exist, splits that add up to the line).
- An edit that replaces a setting carries the fields of the row it replaced (`was`), a scheduled amount included, since the budget keeps the last amount on a date (`editor_scheduled` in Reports lists those in force). If the ledger has moved on since (another change set, or a seed), the edit is stale.
- One change set edits each setting once, by the same target the editor stages by (`editTarget`; a scheduled amount is one per line and date, a pair of lines one pair either way round).
- One bad or stale edit refuses the whole file, which stays in the inbox with every reason, shown on the status page and in the Saved tab, where Discard moves it to the trash.

To deploy (Node 22 and `npm i -g @google/clasp`):

1. `cd web && npm ci && npm run build`
2. `clasp login`, then `clasp create-script --type webapp --title "Household views" --rootDir dist` (or copy `.clasp.json.example` to `.clasp.json` with an existing script id)
3. `clasp push` (or `npm run push`, which builds first)
4. In the script editor, Project Settings, Script properties: add `REPORTS_ID` with the Reports spreadsheet's id
5. Deploy, New deployment, Web app. It runs as the person viewing it, so they see only what they can open; `access` in `appsscript.json` is `MYSELF` (only the owner). To let another household member open it, set `ANYONE` (any signed-in Google account; Reports' own sharing still decides who can read it) and redeploy.
6. After a change: check out the release tag, `npm run push`, then `clasp update-deployment <deployment id>` (`clasp list-deployments` shows it), so the web app's URL stays the same. A release that adds a permission (editing added `drive.file` and the Drive service) asks for it again the next time the page opens.
